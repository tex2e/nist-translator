概要

More than 100 years ago, Lord Kelvin insightfully observed that measurement is vital to deep knowledge and understanding in physical science. During the last few decades, researchers have made various attempts to develop measures and systems of measurement for computer security with varying degrees of success. This paper provides an overview of the security metrics area and looks at possible avenues of research that could be pursued to advance the state of the art.

Security metrics is an area of computer security that has been receiving a good deal of attention lately. It is not a new topic, but one which receives focused interest sporadically. Much of what has been written about security metrics is definitional, aimed at providing guidelines for defining a security metric and specifying criteria for which to strive. However, relatively little has been reported on actual metrics that have been proven useful in practice [Ber05, CIS08].

原本 PDF p.6

セキュリティメトリクスは、コンピュータセキュリティの分野の一つで、最近多くの注目を集めています。新しい話題ではありませんが、関心が集中するのは散発的です。セキュリティメトリクスについて書かれたものの多くは定義に関するもので、セキュリティメトリクスを定義するためのガイドラインと、目指すべき基準の規定を目的としています。しかし、実務で有用であると実証された実際のメトリクスについての報告は、比較的わずかです [Ber05, CIS08]。

Information security metrics are seen as an important factor in making sound decisions about various aspects of security, ranging from the design of security architectures and controls to the effectiveness and efficiency of security operations. Security metrics strive to offer a quantitative and objective basis for security assurance. The main uses fall into several broad classes:

原本 PDF p.6

情報セキュリティメトリクスは、セキュリティアーキテクチャや管理策の設計から、セキュリティ運用の有効性と効率に至るまで、セキュリティのさまざまな側面について適切な判断を下すための重要な要素と見られています。セキュリティメトリクスは、セキュリティ保証に対する定量的で客観的な根拠の提供を目指しています。主な用途は、いくつかの大きな区分に分けられます。

•Strategic support – Assessments of security properties can be used to aid different kinds of decision making, such as program planning, resource allocation, and product and service selection.

原本 PDF p.6

•戦略的支援 – セキュリティ特性の評価は、プログラム計画、リソース配分、製品やサービスの選定など、さまざまな種類の意思決定の補助に使えます。

•Quality assurance – Security metrics can be used during the software development lifecycle to eliminate vulnerabilities, particularly during code production, by performing functions such as measuring adherence to secure coding standards, identifying likely vulnerabilities that may exist, and tracking and analyzing security flaws that are eventually discovered.

原本 PDF p.6

•品質保証 – セキュリティメトリクスは、ソフトウェア開発ライフサイクルの間、特にコード作成中に、セキュアコーディング標準の遵守状況の測定、存在する可能性の高い脆弱性の特定、最終的に発見されるセキュリティ上の欠陥の追跡と分析といった機能を果たすことで、脆弱性を排除するために使えます。

•Tactical oversight – Monitoring and reporting of the security status or posture of an IT system can be carried out to determine compliance with security requirements (e.g., policy, procedures, and regulations), gauge the effectiveness of security controls and manage risk, provide a basis for trend analysis, and identify specific areas for improvement.

原本 PDF p.6

•戦術的な監督 – IT システムのセキュリティの状況や態勢の監視と報告を行うことで、セキュリティ要件（例: ポリシー、手順、規制）への準拠の判定、セキュリティ管理策の有効性の評価とリスクの管理、傾向分析の基礎の提供、改善すべき具体的な領域の特定ができます。

Security metrics can be categorized various ways. One simple classification is to consider metrics that denote the maturity level of processes believed to contribute to the security of a system, versus those that denote the extent to which some security characteristic is present in a system [Jel00]. The former apply to security processes, procedures, and training used when designing, configuring, maintaining, and operating a system. The latter apply to the security posture of a system and the inherent level of risk involved. More elaborate security metric taxonomies also exist [Vau02, Sav07].

原本 PDF p.6

セキュリティメトリクスは、さまざまな方法で分類できます。単純な分類の一つは、システムのセキュリティに寄与すると考えられるプロセスの成熟度レベルを表すメトリクスと、何らかのセキュリティ特性がシステムにどの程度備わっているかを表すメトリクスとを区別するものです [Jel00]。前者は、システムの設計、構成、保守、運用の際に使われるセキュリティのプロセス、手順、トレーニングに適用されます。後者は、システムのセキュリティ態勢と、そこに内在するリスクのレベルに適用されます。より精緻なセキュリティメトリクスの分類体系も存在します [Vau02, Sav07]。

Other disciplines, such as the field of finance, have proven quantitative methods for determining risk along with decision-making frameworks based on established measures and metrics. Such standardized measurements and decision-aid capabilities are just emerging for information system security, however, and as in any discipline, require realistic assumptions and inputs to attain reliable results [Sal09]. Advancing the state of scientifically sound, security measures and metrics (i.e., a metrology for information system security) would greatly aid the design, implementation, and operation of secure information systems.

原本 PDF p.7

金融分野などの他の分野には、確立された尺度とメトリクスに基づく意思決定の枠組みと、リスクを判定するための実績ある定量的手法があります。しかし、情報システムセキュリティにおけるこのような標準化された測定と意思決定支援の能力は、ようやく現れ始めたところです。また、どの分野でも同様に、信頼できる結果を得るには現実的な前提と入力が必要です [Sal09]。科学的に健全なセキュリティ測定とメトリクス（すなわち、情報システムセキュリティの計量学）の現状を前進させることは、安全な情報システムの設計、実装、運用に大いに役立ちます。

原本 PDF p.8

2. 背景

The term “security metrics” is used often today, but with a range of meanings and interpretations. Several examples taken from recent publications are as follows:

原本 PDF p.8

「セキュリティメトリクス」という用語は今日よく使われていますが、その意味や解釈はさまざまです。最近の刊行物から取った例をいくつか示します。

“At a high-level, metrics are quantifiable measurements of some aspect of a system or enterprise. For an entity (system, product, or other) for which security is a meaningful concept, there are some identifiable attributes that collectively characterize the security of that entity. Further, a security metric (or combination of security metrics) is a quantitative measure of how much of that attribute the entity possesses. A security metric can be built from lower-level physical measures.” [ISS08]

原本 PDF p.8

「大まかに言えば、メトリクスとは、システムやエンタープライズのある側面を定量化可能な形で測定したものです。セキュリティが意味のある概念であるエンティティ（システム、製品など）には、そのエンティティのセキュリティを総合的に特徴づける、識別可能な属性がいくつかあります。さらに、セキュリティメトリクス（またはセキュリティメトリクスの組み合わせ）は、エンティティがその属性をどの程度備えているかを示す定量的な尺度です。セキュリティメトリクスは、より低レベルの物理的な尺度から構築できます。」 [ISS08]

“Metrics are tools designed to facilitate decision making and improve performance and accountability through collection, analysis, and reporting of relevant performance-related data. The purpose of measuring performance is to monitor the status of measured activities and facilitate improvement in those activities by applying corrective actions, based on observed measurements. … While a case can be made for using different terms for more detailed and aggregated items, such as ‘metrics’ and ‘measures,’ this document uses these terms interchangeably.” [Swa03]

原本 PDF p.8

「メトリクスは、性能に関するデータの収集、分析、報告を通じて、意思決定を容易にし、性能と説明責任を向上させるために設計されたツールです。性能測定の目的は、測定対象の活動の状況を監視し、観測された測定値に基づいて是正措置を講じることで、その活動の改善を促すことです。…「メトリクス」と「測定値」のように、より詳細な項目と集約された項目に異なる用語を使い分けるべきだという主張もありますが、この文書ではこれらの用語を同じ意味で使います。」 [Swa03]

“Measurements provide single-point-in-time views of specific, discrete factors, while metrics are derived by comparing to a predetermined baseline two or more measurements taken over time. Measurements are generated by counting; metrics are generated from analysis. In other words, measurements are objective raw data and metrics are either objective or subjective human interpretations of those data.” [Pay06]

原本 PDF p.8

「測定値は、特定の個別の要素についてある時点を切り取った見方を与えますが、メトリクスは、時間をかけて取得した 2 つ以上の測定値を、あらかじめ定めたベースラインと比較することで導き出されます。測定値は計数によって生成され、メトリクスは分析から生成されます。言い換えると、測定値は客観的な生データであり、メトリクスは、それらのデータに対する客観的または主観的な人間の解釈です。」 [Pay06]

A metric generally implies a system of measurement based on quantifiable measures. A method of measurement used to determine the unit of a quantity can involve a measuring instrument, reference material, or measuring system. Measured values of properties should be linearly ordered and the method of measurement well defined, including details of how specific factors are to be measured or assessed and explanations of sources of uncertainty.

原本 PDF p.8

メトリクスは一般に、定量化可能な尺度に基づく測定体系を意味します。ある量の単位を決定するために使われる測定方法では、測定器、標準物質、または測定システムを使用することがあります。特性の測定値は線形に順序づけられるべきです。また、測定方法は、特定の要素をどのように測定または評価するかの詳細や、不確かさの発生源の説明を含めて、明確に定義されるべきです。

For information system security, the measures are concerned with aspects of the system that contribute to its security. That is, security metrics involve the application of a method of measurement to one or more entities of a system that possess an assessable security property to obtain a measured value. From an organizational perspective, security measures and metrics should enable an organization to gauge how well it is meeting its security objectives.

原本 PDF p.8

情報システムセキュリティでは、尺度は、システムのセキュリティに寄与するシステムの側面に関係します。つまり、セキュリティメトリクスは、評価可能なセキュリティ特性を持つシステムの1つ以上のエンティティに測定方法を適用して、測定値を得ることを伴います。組織の観点からは、セキュリティ測定とメトリクスにより、組織が自らのセキュリティ目標をどの程度達成しているかを評価できるようにすべきです。

To be of value, the method of measurement employed should be reproducible, that is, capable of attaining the same result when performed independently by different competent evaluators. The result should also be repeatable, such that a second assessment by the same evaluators produces the same result. Relevance and timeliness are also implicit considerations, since it is of little benefit to have measures that are not meaningful or whose latency exceeds their usefulness.

原本 PDF p.8

価値を持つには、採用する測定方法は再現可能であるべきです。すなわち、異なる有能な評価者が独立して実施しても同じ結果が得られるべきです。結果も反復可能であるべきであり、同じ評価者による2回目の評価でも同じ結果が得られるべきです。意味のない尺度や、遅延が有用性を上回る尺度を持っても利益はほとんどないため、関連性と適時性も暗黙の考慮事項です。

Note that the term “metrics” when used in the context of Information Technology (IT) is a bit of misnomer.1 It implies that traditional concepts in metrology, as used in physics and other areas of science and technology, apply equally to IT. That is not the case, however [Gra99, Vau02]. For example, the concepts of fundamental units, scales, and uncertainty prevalent in scientific metrics have not traditionally been applied to IT or have been applied less rigorously. It is also important to recognize that compared with more mature scientific fields, IT metrology is still emerging. Many physical properties began as a qualitative comparison (e.g., “warmer” and “colder”) before becoming a formally defined quantity (e.g., “temperature”), which holds promise for IT metrics in general, and IT system security metrics in particular.

原本 PDF p.9

情報技術（IT）の文脈で用語「メトリクス」を使うことは、やや誤称であることに注意してください。1 これは、物理学やその他の科学技術分野で使われる従来の計量学の概念が、IT にも同様に当てはまることを暗示しています。しかし、そうではありません [Gra99, Vau02]。たとえば、科学的なメトリクスで一般的な基本単位、尺度、不確かさの概念は、従来 IT には適用されてこなかったか、適用されても厳密さに欠けていました。より成熟した科学分野と比べて、IT の計量学はまだ発展途上であることを認識することも重要です。多くの物理的特性は、正式に定義された量（例: 「温度」）になる前は、定性的な比較（例: 「より暖かい」と「より冷たい」）から始まりました。このことは、IT メトリクス全般、特に IT システムのセキュリティメトリクスに期待を抱かせます。

While some movement toward quantitative metrics for IT system security exists, in practice, qualitative measures that reflect reasoned estimates of security by an evaluator are the norm. That is, measures of information system security properties are often based on an evaluator’s expertise, intuition, and insight to induce an ordering, which is then quantified (e.g., 1=low, 2=medium, 3=high). Because of the subjectivity involved, some of the attributes sought in a good metric are not readily obtainable. For example, results in penetration testing or other methods of assessment that involve specialized skills are sometimes not repeatable, since they rely on the knowledge, talent, and experience of an individual evaluator, which can differ from other evaluators with respect to a property being measured.

3.1 Correctness and Effectiveness

原本 PDF p.10

3.1 正確性と有効性

Security of an IT system comprises two interdependent aspects: correctness and effectiveness. Correctness denotes assurance that the security-enforcing mechanisms have been rightly implemented (i.e., they do exactly what they are intended to do, such as performing some calculation). Effectiveness denotes assurance that the security-enforcing mechanisms of the system meet the stated security objectives (i.e., they do not do anything other than what is intended for them to do, while satisfying expectations for resiliency). Most programmers have produced a program that satisfies correctness criteria, but fails to meet effectiveness criteria, particularly under extraordinary unanticipated conditions.

原本 PDF p.10

ITシステムのセキュリティは、相互に依存する2つの側面、すなわち正確性と有効性から成ります。正確性は、セキュリティ実施機構が正しく実装されている（すなわち、何らかの計算を行うなど、意図されたことを正確に行う）という保証を表します。有効性は、システムのセキュリティ実施機構が、定められたセキュリティ目標を満たしている（すなわち、レジリエンスへの期待を満たしつつ、意図されたこと以外は何も行わない）という保証を表します。ほとんどのプログラマーは、正確性の基準は満たすものの、有効性の基準は満たさないプログラムを作ったことがあります。特に、想定外の異常な状況でそうなることがあります。

The evaluation of correctness gauges the ability of the security-enforcing mechanisms to carry out their tasks precisely to the specifications. Correctness can be assessed with respect to the development process and the development environment during the construction of the system and also in terms of its operation. Emphasis is typically on substantiating how well the system exhibits the behavior expected of it.

原本 PDF p.10

正確性の評価は、セキュリティ実施機構が仕様どおりに正確にタスクを実行する能力を測ります。正確性は、システムの構築中の開発プロセスや開発環境に関して、また運用に関しても評価できます。通常は、システムが期待された動作をどれだけ示すかを実証することに重点が置かれます。

The evaluation of effectiveness gauges the strength of the security-enforcing mechanisms to withstand attacks in carrying out their function. Effectiveness requires ascertaining how well the security-enforcing components tie together and work synergistically, the consequences of any known or discovered vulnerabilities, and the usability of the system. Emphasis is typically on substantiating whether the system can be induced to exhibit behavior that leads to or demonstrates a security vulnerability.

原本 PDF p.10

有効性の評価は、セキュリティ実施機構が、その機能を実行するうえで攻撃に耐える強度を測ります。有効性には、セキュリティ実施の構成要素がどれだけうまく結び付いて相乗的に機能するか、既知または発見された脆弱性の影響、およびシステムの使いやすさを確かめることが必要です。通常は、システムを誘導して、セキュリティ上の脆弱性につながる、またはそれを示す動作をさせられるかどうかを実証することに重点が置かれます。

In practice, security evaluations of correctness and effectiveness are largely done through reasoning rather than direct measurement of actual hardware and software components. Often, simplifying assumptions are made. For example, it may be postulated that the system communicates only with other systems operating under the same management control and security policy constraints; the need to trust and communicate with external systems under different management control would not be specifically addressed [SAI07]. The emphasis on abstractions and simplifying assumptions dissociates the assessment results from actual operational use [Lit93]. Even with this emphasis, the correctness and effectiveness of significantly large systems cannot be accurately determined for higher levels of assurance. Because of the high degree of human element involved, the timeliness and reproducibility of results also come into question. Conventions and practices, such as standardized procedures and criteria, can be applied to help normalize results among evaluators and expedite the process. Technical refresher classes and conformance training are other useful practices. Nevertheless, unless more of the human element can be eliminated or replaced by automated means, the current conditions can be expected to persist.

原本 PDF p.11

実際には、正確性と有効性に関するセキュリティ評価は、実際のハードウェアやソフトウェアの構成要素を直接測定するのではなく、主に推論によって行われます。多くの場合、単純化の前提が置かれます。たとえば、システムは、同じ管理統制とセキュリティポリシーの制約の下で動作する他のシステムとだけ通信すると仮定される場合があります。異なる管理統制下にある外部システムを信頼して通信する必要性は、具体的には扱われません [SAI07]。抽象化と単純化の前提を重視すると、評価結果が実際の運用から切り離されます [Lit93]。このように重視しても、相当に大規模なシステムの正確性と有効性を、より高い保証レベルについて正確に判定することはできません。人的要素が大きいため、結果の適時性と再現性も問題になります。標準化された手順や基準などの慣行や実務を適用すれば、評価者間で結果を正規化し、プロセスを迅速化できます。技術の再教育講座や適合性のトレーニングも、ほかの有用な実務です。それでも、人的要素をより多く排除するか、自動化された手段で置き換えられない限り、現在の状況は続くと予想されます。

3.2 Leading Versus Lagging Indicators

原本 PDF p.11

3.2 先行指標と遅行指標

Analogous to economic indicators, security metrics may be potentially leading, coincident, or lagging indicators of the actual security state of the system. The distinction is significant. A coincident indicator reflects security conditions happening concurrently, while leading and lagging indicators reflect security conditions that exist respectively before or after a shift in security. If a lagging indicator is treated as a leading or coincident indicator, the consequences due to misinterpretation and reaction can be serious. The longer the latency period is for a lagging indicator, the greater the likelihood for problems. That is, a lagging security metric with a short latency period or lag time is preferred over one with a long latency period, since any needed response to an observed change can take place earlier. It is important to recognize lagging indicators and, if they are used, to be prepared to handle the intrinsic delay and associated limitations.

原本 PDF p.11

経済指標と同様に、セキュリティメトリクスは、システムの実際のセキュリティ状態の先行指標、一致指標、遅行指標のいずれにもなりえます。この区別は重要です。一致指標は同時に起きているセキュリティの状況を反映しますが、先行指標と遅行指標は、それぞれセキュリティの変化の前または後に存在するセキュリティの状況を反映します。遅行指標を先行指標や一致指標として扱うと、誤解とそれに基づく対応によって深刻な結果を招く可能性があります。遅行指標の遅延期間が長いほど、問題が生じる可能性は高くなります。つまり、観測された変化に対して必要な対応をより早く行えるため、遅延期間（遅れ時間）の短い遅行セキュリティメトリクスが、長いものよりも好まれます。遅行指標を認識し、使う場合は、その本質的な遅れと関連する制約に対処する準備をしておくことが重要です。

Simple counts, when used as a security measure, can be especially hard to classify and interpret. For example, does an increase in the number of viruses detected by antivirus software serve as a leading indicator, because the increased activity indicates an elevated threat level; serve as a lagging indicator, because the increased activity demonstrates a highly proficient leading-edge antivirus mechanism; or serve as a coincident indicator, because the increased activity acts as a notification that other security-enforcing mechanisms are failing? Similarly, decreased activity may be because the antivirus mechanism is losing its effectiveness, other security-enforcing mechanisms are increasingly successful, or the system is simply not being subjected to as many attacks.

原本 PDF p.11

単純な計数は、セキュリティの尺度として使う場合、特に分類と解釈が困難になりえます。たとえば、アンチウイルスソフトウェアが検出したウイルス数の増加は、活動の増加が脅威レベルの上昇を示すため先行指標になるのでしょうか。それとも、活動の増加が非常に優れた最先端のアンチウイルス機構を実証しているため遅行指標になるのでしょうか。あるいは、活動の増加が、他のセキュリティ実施機構が機能していないことの通知として働くため、一致指標になるのでしょうか。同様に、活動の減少は、アンチウイルス機構の有効性が低下しているため、他のセキュリティ実施機構がますます成功しているため、またはシステムが受ける攻撃の数が単に減っているためかもしれません。

Many security metrics can be viewed as lagging indicators. The perspective on the initial security assessments of a system, whether they were done by a human evaluator (e.g., through penetration testing or external security audit), automated means (e.g., through vulnerability testing or security log processing), or some combination of the two, is likely to change eventually to reflect a lower security standing and higher associated risk. The main reason is that over time, understanding of a system and its related weaknesses and vulnerabilities deepens, especially in light of successful attacks on the system or other systems sharing similar characteristics that reveal previously unimagined or unexpected avenues of attack. That greater understanding is subsequently addressed in updated assessments (e.g., through additional tests). While some assessment programs have a process to refresh or maintain initial security assessments, a significant delay nevertheless occurs. Stated another way, no metric exists that can denote the state of security of a system in an absolute sense [Tor07a, Tor07b].

原本 PDF p.11

多くのセキュリティメトリクスは遅行指標とみなせます。システムの最初のセキュリティ評価は、人間の評価者（例: ペネトレーションテストや外部のセキュリティ監査による）、自動化された手段（例: 脆弱性試験やセキュリティログの処理による）、またはその両方の組み合わせのいずれで行われたものであっても、それに対する見方は、いずれ、より低いセキュリティ水準と、それに伴うより高いリスクを反映するように変わる可能性が高いです。主な理由は、時間がたつにつれて、システムとそれに関連する弱点や脆弱性の理解が深まるためです。特に、システム自体、または類似の特性を共有する他のシステムに対する攻撃が成功し、これまで想像もしなかった、または予想外の攻撃経路が明らかになった場合にそうなります。その理解の深まりは、その後、更新された評価（例: 追加の試験による）で反映されます。初期のセキュリティ評価を更新または維持するプロセスを持つ評価プログラムもありますが、それでも大きな遅れが生じます。別の言い方をすれば、システムのセキュリティの状態を絶対的な意味で示せるメトリクスは存在しません [Tor07a, Tor07b]。

Patches and software updates that are intended to repair or improve the security-enforcing mechanisms can lessen the significance of a lagging indicator. Not only does a reset of the baseline system occur with each change, potentially increasing risk [Bre07, Kei08, Lem08, Mar08, Nag08], but an exact picture of the initial baseline becomes obscured and more complicated to track over time (e.g., [Sto08]), making revised assessments impractical. That is, the presumed security posture of the initial baseline is never updated in light of increased understanding, potentially giving a false impression of the actual state. Several recent examples of dramatic shifts in our understanding of vulnerabilities in commonly used technologies, such as the Flash Player-ActionScript virtual machine [Dow08], OpenSSL cryptography [Dou08a, Gar08], MD5 algorithm in Web certificates [Pou08], and DNS protocol implementations [Dou08b], and also the prevalence of zero-day vulnerabilities indicate that with hindsight, unrevised values of lagging indicators could be highly misleading.

原本 PDF p.12

セキュリティ実施機構の修復や改善を目的としたパッチやソフトウェア更新は、遅行指標の重要性を低下させることがあります。変更のたびにベースラインシステムのベースラインが再設定され、リスクが増える可能性があるだけでなく [Bre07, Kei08, Lem08, Mar08, Nag08]、初期のベースラインの正確な姿が時間とともに不明瞭になり、追跡がより複雑になる（例: [Sto08]）ため、改訂された評価の実施が現実的でなくなります。つまり、初期のベースラインについて想定されたセキュリティ態勢は、理解が深まっても更新されず、実際の状態について誤った印象を与える可能性があります。Flash Player-ActionScript仮想マシン [Dow08]、OpenSSLの暗号 [Dou08a, Gar08]、Web証明書におけるMD5アルゴリズム [Pou08]、DNSプロトコルの実装 [Dou08b] など、広く使われている技術の脆弱性に対する私たちの理解が劇的に変化した最近のいくつかの例に加え、ゼロデイ脆弱性が広く存在することは、後から振り返ると、改訂されていない遅行指標の値が大きな誤解を招きうることを示しています。

3.3 Organizational Security Objectives

原本 PDF p.12

3.3 組織のセキュリティ目標

Organizations exist for different purposes, hold different assets, have different exposure to the public, face different threats, and have different tolerances to risk. Because of these and other differences, their security objectives can vary significantly. For example, a government organization that mainly handles data about individual citizens of the country (e.g., taxes or social insurance) has different objectives than a government organization that does not (e.g., commerce or education). Similarly, the security objectives of a government organization that prepares and disseminates information for public consumption are different from one that deals mainly with classified information for its own use. In addition, practical considerations apply—most organizations cannot afford financially to protect all computational resources and assets at the highest degree possible and must prioritize based on criticality and sensitivity.

原本 PDF p.12

組織は、目的が異なり、保有する資産が異なり、公衆への露出が異なり、直面する脅威が異なり、リスク許容度が異なります。これらやその他の違いにより、セキュリティ目標は大きく異なる場合があります。たとえば、主にその国の個々の市民に関するデータ（例: 税や社会保険）を扱う政府組織の目標は、そうでない政府組織（例: 商務や教育）の目標とは異なります。同様に、公衆が利用するための情報を作成して普及させる政府組織のセキュリティ目標は、主に自らが使う機密情報を扱う組織のものとは異なります。さらに、現実的な考慮も働きます。ほとんどの組織は、財政的にすべての計算資源と資産を可能な限り最高の水準で保護する余裕がなく、重要度と機微性に基づいて優先順位を付けなければなりません。

Security metrics are generally used to determine how well an organization is meeting its security objectives. Since the security objectives of organizations can vary widely, it is reasonable to expect that the metrics required to make such an assessment for one organization would also be very different from those used for another. In other words, security is risk and policy dependent from an organizational perspective; the same platform populated with data at the same level of sensitivity, but from two different organizations, could be deemed adequate for one and inadequate for the other. The implication is that establishing security metrics that could be used for meaningful system comparisons between organizations would be extremely difficult to achieve (i.e., if achieved, they would have little real significance for some organizations).

原本 PDF p.12

セキュリティメトリクスは一般に、組織が自らのセキュリティ目標をどの程度達成しているかを判断するために使われます。組織のセキュリティ目標は大きく異なりうるため、そのような評価を行うために必要なメトリクスも、ある組織と別の組織で大きく異なると予想するのが妥当です。言い換えると、組織の観点からは、セキュリティはリスクとポリシーに依存します。同じ機微性レベルのデータを搭載した同じプラットフォームでも、2 つの異なる組織のものであれば、一方にとっては適切、他方にとっては不適切と判断されることがあります。このことが示唆するのは、組織間で意味のあるシステム比較に使えるセキュリティメトリクスを確立するのは、達成が極めて難しいということです（すなわち、達成できたとしても、一部の組織にとってはほとんど実際の意味がありません）。

Although security objectives are unique and tied to the goals and purpose of an organization, similarities in high level security objectives do exist between organizations performing similar work and are sometimes captured as best practices. Some steps, such as standard security profiles of organizational security requirements and criteria, can be taken to standardize common sets of core requirements needed by comparable organizations and allow reuse of engineered solutions. However, at best they cover only a common subset of the entire picture and may focus mainly on technical metrics.

原本 PDF p.13

セキュリティ目標は固有のものであり、組織の目標や目的に結び付いていますが、類似の業務を行う組織の間には、上位レベルのセキュリティ目標に類似点があり、それがベストプラクティスとして捉えられることもあります。組織のセキュリティ要件と基準の標準的なセキュリティプロファイルなど、いくつかの手段を講じれば、同等の組織が必要とする中核的な要件の共通の集合を標準化し、設計済みのソリューションの再利用を可能にできます。しかし、これらが扱うのは、せいぜい全体像の共通の一部にすぎず、主に技術的なメトリクスに焦点を当てている可能性があります。

3.4 Qualitative and Quantitative Properties

原本 PDF p.13

3.4 定性的な特性と定量的な特性

Measurement of software properties in general has been difficult to accomplish.2 Many desired properties such as complexity, usability, and scalability are qualities that can be expressed in general terms, but difficult to define in objective terms that are useful in practice and provide a fully complete picture. For example, two well known software complexity measures, the McCabe cyclomatic complexity metric and Halstead's software science metric, determine program complexity directly from source code [Mar97]. Critics claim that the number of control paths McCabe used to determine the complexity of code is only one part of the total picture. Similarly, some consider the emphasis placed on lexical and textual measures by Halstead to be weak, because the structural or logic flow is ignored, and consider the assumptions used to derive complexity equations to be faulty; furthermore, the equations can be difficult to compute and practical use is limited to comparisons between versions of the same code. At best, certain properties of software that are assessed are able to capture only some facets of any desired quality.

原本 PDF p.13

ソフトウェアの特性の測定は、一般に達成が難しいものでした。2 複雑さ、使いやすさ、スケーラビリティなど、望まれる特性の多くは、一般的な言葉で表現できる性質ですが、実務で有用で、完全な全体像を示す客観的な言葉で定義することは困難です。たとえば、よく知られた 2 つのソフトウェア複雑さの尺度である McCabe のサイクロマティック複雑度メトリクスと Halstead のソフトウェアサイエンスメトリクスは、ソースコードから直接プログラムの複雑さを判定します [Mar97]。批評家は、McCabe がコードの複雑さを判定するために用いた制御パスの数は、全体像の一部にすぎないと主張しています。同様に、Halstead が語彙的・テキスト的な尺度に置いた重点は、構造やロジックの流れを無視しているため弱いと考える人もおり、複雑さの式を導くために用いた仮定は誤っていると考える人もいます。さらに、これらの式は計算が困難な場合があり、実用上の利用は同じコードのバージョン間の比較に限られます。せいぜい、評価されるソフトウェアの特定の特性が、望まれる品質のいくつかの面しか捉えられないのが関の山です。

The distinction between quantitative and qualitative security metrics is easily obscured [Hen01]. Qualitative assignments can be used to represent quantitative measures of security properties (e.g., low means no vulnerabilities found; medium, between one and five found; and high, more than five found). More often, numeric values are used to represent rankings that are otherwise qualitative (e.g., 1, 2, and 3, versus low, medium, and high). While the numeric difference between ranked values may be significant for some metrics, it may not be for others, which is often the case with security metrics. For example, the numeric difference between security rankings assigned through the analysis and reasoning of evaluators would likely not have any particular significance, other than to impart an ordering. In other words, the common scales of measurement (i.e., nominal, ordinal, interval, and ratio) and associated principles of use apply.

原本 PDF p.13

定量的なセキュリティメトリクスと定性的なセキュリティメトリクスの区別は、容易に曖昧になります [Hen01]。定性的な割り当てを使って、セキュリティ特性の定量的な尺度を表すことができます（例: 低は脆弱性が見つからなかったことを、中は 1 件から 5 件見つかったことを、高は 5 件を超えて見つかったことを表す）。より多くの場合は、本来は定性的な順位を表すために数値が使われます（例: 低・中・高に対する 1、2、3）。順位づけされた値の間の数値上の差は、一部のメトリクスでは意味を持つこともありますが、セキュリティメトリクスでよくあるように、ほかのメトリクスでは意味を持たない場合があります。たとえば、評価者の分析と推論によって割り当てられたセキュリティ順位の間の数値上の差は、順序を与えること以外には、特に重要な意味を持たない可能性が高いです。言い換えると、一般的な測定尺度（すなわち、名義尺度、順序尺度、間隔尺度、比率尺度）と、それに関連する使用上の原則が当てはまります。

Quantitative valuations of several security properties may also be weighted and combined to derive a composite value (e.g., rating = .25 * rankingA + .75 * rankingB). Such compositions can, however, yield undesired results. Some qualitative properties are intangible and not able to be captured via direct measurement. An attribute, such as beauty, scent, or flavor, can be highly subjective in nature, varying widely among individuals. Software security assessments appear to share many of the traits of these types of assessments and, where applicable, could possibly benefit by adopting or adapting some of the techniques used.

3.5 Measurements of the Large Versus the Small

原本 PDF p.14

3.5 大規模なものの測定と小規模なものの測定

Security measurements have proven to be much more successful when the target of assessment is small and simple rather than large and complex. For example, a FIPS 140 evaluation, which focuses exclusively on cryptographic modules, generally requires less cost and time than a Common Criteria evaluation of a product that incorporates such modules. This is not too surprising, since larger systems generally have greater complexity and functionality. As the number of components in a system increases, the number of possible interactions increases with the square of the number of components. Greater complexity and functionality typically relate inversely to security and require more scrutiny to evaluate.

原本 PDF p.14

セキュリティ測定は、評価の対象が大規模で複雑なものではなく、小規模で単純なものである場合のほうが、はるかに成功しやすいことが実証されています。たとえば、暗号モジュールだけに焦点を当てる FIPS 140 の評価は、一般に、そのようなモジュールを組み込んだ製品の Common Criteria 評価よりも、費用と時間が少なくて済みます。大規模なシステムは一般に、複雑さと機能がより大きいため、これはさほど意外ではありません。システム内の構成要素の数が増えると、起こりうる相互作用の数は構成要素の数の 2 乗に比例して増えます。複雑さと機能が大きいほど、通常はセキュリティと逆の関係になり、評価にはより多くの精査が必要になります。

Physical analogies apply here. The strength of a single concrete block of uniform material is more readily determined than a wall or structure composed of these blocks. The latter involve binding and reinforcing materials as well as height, design, and other architectural considerations. In other words, the different materials involved and the way in which they are composed determine the overall strength.

原本 PDF p.14

ここでは物理的なたとえが当てはまります。均一な材料でできた 1 つのコンクリートブロックの強度は、そのブロックを積んで作った壁や構造物の強度よりも、容易に判定できます。後者には、高さ、設計、その他の建築上の考慮事項のほか、結合材や補強材が関わります。言い換えると、関与するさまざまな材料と、それらを組み合わせる方法が、全体の強度を決めます。

The composability problem in security is a long-standing problem—two systems, both of which are judged to be secure, can be connected together such that the resulting composite system is not secure. In theory, evaluated systems could be designed to be predictably composable such that the properties of the resulting composite system are easily determined. In practice, this has not occurred. Composability is somewhat like the philosopher’s stone, a legendary substance that could change cheap metals into gold. A solution for building meaningful, complex software systems from components may exist theoretically; however, progress to date in achieving this goal has been limited, suggesting that composability is an elusive problem that may be solvable only in limited situations.

原本 PDF p.14

セキュリティにおける合成可能性の問題は、長年の問題です。どちらも安全と判断された 2 つのシステムを接続すると、結果として得られる合成システムが安全でなくなることがあります。理論上は、評価されたシステムを予測可能に合成できるように設計し、結果として得られる合成システムの特性を容易に判定できるようにすることもできます。実際には、そうはなっていません。合成可能性は、卑金属を金に変えられるとされる伝説上の物質である、哲学者の石に少し似ています。構成要素から意味のある複雑なソフトウェアシステムを構築するための解決策は、理論的には存在するかもしれませんが、この目標の達成に向けたこれまでの進展は限られており、合成可能性は、限られた状況でしか解決できない、捉えどころのない問題である可能性を示唆しています。

A technological breakthrough in composability would be a way to have security measurements of small systems directly contribute to the measurements of larger systems of which they are a part. In the absence of sound security metrics that can be used to assess the security of composed systems made from composable components with measured properties, the current high latency and expense in evaluating large systems can be expected to continue and limit the ability to perform cross-system comparisons in security.

原本 PDF p.14

合成可能性における技術的なブレークスルーとは、小規模なシステムのセキュリティ測定が、それらを構成要素として含む大規模なシステムの測定に直接寄与する方法を得ることでしょう。測定された特性を持つ合成可能な構成要素から作られた合成システムのセキュリティを評価するために使える、妥当なセキュリティメトリクスがなければ、大規模システムの評価における現在の高い遅延と費用は今後も続き、セキュリティにおけるシステム間比較を行う能力を制限すると予想されます。

4.1 Formal Models of Security Measurement and Metrics

原本 PDF p.15

4.1 セキュリティ測定とメトリクスの形式モデル

Security measurement and metrics efforts that are conceived at a high level of abstraction and formalism are often difficult to interpret and apply in practice. Existing formalisms also pose difficulties to reconcile with actual operational environments where software patches, version updates, and configuration setting changes take place regularly. The absence of formal security models and other formalisms needed to improve the relevance of security metrics to deployed systems have hampered progress. Having formal models that depict security properties of operational IT systems and incorporate relevant objects of significance to system security measurement would be a useful contribution. The research goal is to establish formal models with a level of detail sufficient to enable realistic predictions of operational system behavior and portray security measurements accurately.

原本 PDF p.15

高い抽象度と形式性で着想されたセキュリティ測定とメトリクスの取り組みは、実際に解釈して適用することが難しいことが少なくありません。既存の形式的手法は、ソフトウェアパッチ、バージョン更新、設定変更が定期的に行われる実際の運用環境との整合を図るのも困難です。セキュリティメトリクスと展開済みシステムとの関連性を高めるために必要な、形式的なセキュリティモデルやその他の形式的手法が存在しないことが、進展を妨げてきました。運用中の IT システムのセキュリティ特性を描き、システムのセキュリティ測定にとって重要な関連オブジェクトを組み込んだ形式モデルを持つことは、有用な貢献になるでしょう。研究の目標は、運用システムの動作を現実的に予測し、セキュリティ測定を正確に描くのに十分な詳細さを持つ形式モデルを確立することです。

An example of the type of work expected is the effort on attack surface metrics done at Carnegie Mellon University [Man05, Man07]. A formal model is defined from an intuitive notion of a system’s attack surface (i.e., the ways in which the system can be entered and successfully attacked). The formal model is characterized in terms of certain system resources—those methods (e.g., application programming interfaces), channels (e.g., sockets), and data items (e.g., input strings) that an attacker can use to cause damage to the system. A surface measurement model can then be applied to compare attack surface measurements along each of the three dimensions and used to determine whether one system is more secure than another. The measurements entail making estimates of the damage potential and effort required, which respectively are the level of harm the attacker can cause to the system when using the resource in an attack, and the amount of work needed by the attacker to obtain the necessary access rights to be able to use the resource in an attack.

原本 PDF p.15

期待される研究の一例として、Carnegie Mellon University で行われた攻撃対象領域メトリクスの取り組みがあります [Man05, Man07]。形式モデルは、システムの攻撃対象領域（すなわち、システムに侵入して攻撃を成功させられる方法）という直観的な概念から定義されます。この形式モデルは、攻撃者がシステムに損害を与えるために使える特定のシステムリソース、すなわち、メソッド（例: アプリケーションプログラミングインタフェース）、チャネル（例: ソケット）、データ項目（例: 入力文字列）によって特徴づけられます。その後、対象領域の測定モデルを適用して、3 つの次元それぞれについて攻撃対象領域の測定値を比較し、一方のシステムが他方より安全かどうかを判定するのに使えます。この測定には、損害を与える可能性と必要な労力の見積もりが必要です。これらはそれぞれ、攻撃者がリソースを攻撃で使用した場合にシステムに与えられる被害の度合い、および攻撃者がリソースを攻撃で使用できるようにするために必要なアクセス権を得るのに要する作業量です。

Model checking, a method for formally verifying properties of systems, is another area where a formal technique may have potential for use in security metrics. Properties of interest are expressed as logic formulas. A representation of the system (e.g., a formal or program language description) is traversed and checked to determine whether a property holds, using efficient symbolic algorithms. Specifying security properties of interest to be automatically checked could automate certain types of evaluation. For example, model checking has been used to identify an important class of security vulnerabilities in the Red Hat Linux 9 distribution. Vulnerabilities were expressed as temporal safety properties that described the conditions under which the vulnerabilities were absent from the software programs that made up the distribution [Sch05]. Programs that violated a property were not verifiable and flagged for review. Model checking has also been used to verify security properties of access control policies [Gue04, Rei07b].

原本 PDF p.16

モデル検査は、システムの特性を形式的に検証する手法であり、形式的な技法をセキュリティメトリクスに利用できる可能性のある、もう一つの分野です。対象とする特性を論理式で表現します。システムの表現（例: 形式的な記述やプログラミング言語による記述）をたどり、効率的な記号的アルゴリズムを使って、特性が成り立つかどうかを確認します。対象とするセキュリティ特性を指定して自動的に検査させれば、特定の種類の評価を自動化できる可能性があります。たとえば、モデル検査は、Red Hat Linux 9 ディストリビューションにおける重要な種類のセキュリティ脆弱性を特定するために使われました。脆弱性は、ディストリビューションを構成するソフトウェアプログラムに脆弱性がない条件を記述した、時相安全性特性として表現されました [Sch05]。特性に違反したプログラムは検証できず、レビューのためにフラグが立てられました。モデル検査はまた、アクセス制御ポリシーのセキュリティ特性の検証にも使われています [Gue04, Rei07b]。

Research into formal models could also benefit the design of decision support systems that manage security infrastructure risks by strongly embracing security metrics in determining security investments. Developing decision support models that incorporate technical and organizational aspects of a system and also quantify the utility of a security investment based on established principles would be the focus. The high level of detail and complexity of such models would likely depend strongly on the availability of essential empirical data. For instance, the QuERIES methodology and underlying attack-versus-protect economic model, which offers a means to determine investment levels and strategies for protecting intellectual property in complex systems, requires such data as asset valuations, the costs of protection and theft of assets, and theft probabilities [Car08].

原本 PDF p.16

形式モデルの研究は、セキュリティ投資の決定にセキュリティメトリクスを強く取り入れることで、セキュリティ基盤のリスクを管理する意思決定支援システムの設計にも役立つ可能性があります。焦点となるのは、システムの技術的側面と組織的側面を組み込み、確立された原則に基づいてセキュリティ投資の効用を定量化する、意思決定支援モデルの開発です。このようなモデルの詳細度と複雑さが高くなると、不可欠な経験的データを利用できるかどうかに強く依存する可能性が高いです。たとえば、複雑なシステムにおける知的財産を保護するための投資水準と戦略を決定する手段を提供する QuERIES 手法とその基盤となる攻撃対防御の経済モデルでは、資産評価額、保護と資産窃取のコスト、窃取確率などのデータが必要です [Car08]。

4.2 Historical Data Collection and Analysis

原本 PDF p.16

4.2 過去のデータの収集と分析

Predictive estimates of the security of software components and applications under consideration should be able to be drawn from historical data collected about the characteristics of other similar types of software (e.g., code quality and complexity) and the vulnerabilities they experienced (e.g., number and severity). For example, models that define software reliability in terms of the number of faults in a body of code have been applied to the OpenBSD operating system to estimate characteristics about the number of faults remaining in the system and when those faults may cause failures [Ozm06]. Empirical evidence also exists that features correlate with vulnerabilities and that components containing past vulnerabilities can be used to predict with reasonable accuracy vulnerable components (i.e., those having undiscovered vulnerabilities) based on their features [Neu07]. At the very least, insight into security measurements would likely be gained by applying analytical techniques to such historical collections to identify trends and correlations (e.g., via statistical methods), to discover unexpected relationships (e.g., via data mining), and to reveal other predictive interactions that may exist (e.g., via visual analytics).

原本 PDF p.16

検討中のソフトウェア構成要素とアプリケーションのセキュリティに関する予測的な推定は、他の同種のソフトウェアの特性（例: コードの品質と複雑さ）と、それらが経験した脆弱性（例: 数と深刻度）について収集された過去のデータから導けるべきです。たとえば、コード本体における欠陥の数でソフトウェア信頼性を定義するモデルが、OpenBSD オペレーティングシステムに適用され、システムに残る欠陥の数と、それらの欠陥が障害を引き起こす可能性のある時期についての特性が推定されました [Ozm06]。また、特徴が脆弱性と相関すること、そして過去の脆弱性を含む構成要素を使えば、特徴に基づいて脆弱な構成要素（すなわち、未発見の脆弱性を持つもの）を妥当な精度で予測できることを示す経験的証拠もあります [Neu07]。少なくとも、このような過去の収集データに分析技術を適用して、傾向と相関を特定したり（例: 統計的手法による）、予想外の関係を発見したり（例: データマイニングによる）、存在しうるほかの予測的な相互作用を明らかにしたり（例: ビジュアルアナリティクスによる）することで、セキュリティ測定に対する洞察が得られる可能性が高いです。

The research goal is to identify characteristics of software components and applications in the collection that can be extracted and used to predict the security condition of other software. Available open source software repositories can serve as a starting point for the data collection, but will require additional effort to incorporate vulnerability information and identify the points at which known vulnerabilities first appeared in the code set. With a large enough data collection, reliable estimators of the overall effectiveness of software might be derived that could be used in security assessments of software.

原本 PDF p.17

研究の目標は、収集したデータの中から、ソフトウェア構成要素とアプリケーションの特性のうち、抽出して他のソフトウェアのセキュリティ状態の予測に使えるものを特定することです。利用可能なオープンソースソフトウェアのリポジトリを、データ収集の出発点にできますが、脆弱性情報を組み込み、既知の脆弱性がコードセットに最初に現れた時点を特定するための追加の作業が必要になります。十分に大規模なデータ収集があれば、ソフトウェアの全体的な有効性について、ソフトウェアのセキュリティ評価に使える信頼性の高い推定量を導出できるかもしれません。

A historical data collection has other potential benefits and use. It can serve as a basis for confirming the validity of independently proposed security measurements and methods of measurement, identifying whether associated measures are leading, lagging, or coincident indicators, and establishing estimates of latency and uncertainty for useful indicators. It can also serve as a means to investigate new methods of detecting and discovering both expected and unexpected relationships for use as estimators, and to develop new and improved mathematical and computational methodologies to improve the visual analytics of the data collection. A selected subset of the historical data collection could also be used as reference materials for training or rating the proficiency of security evaluators.

原本 PDF p.17

過去のデータ収集には、ほかにも潜在的な利点と用途があります。独立に提案されたセキュリティ測定と測定方法の妥当性を確認する基礎として、関連する尺度が先行指標、遅行指標、一致指標のいずれであるかを識別する基礎として、また、有用な指標について遅れと不確かさの推定値を確立する基礎として使えます。さらに、推定量として使うために、予想される関係と予想外の関係の両方を検出・発見する新しい方法を調べる手段として、また、データ収集のビジュアルアナリティクスを改善するための、新規で改良された数学的・計算論的方法論を開発する手段としても使えます。過去のデータ収集から選んだ部分集合は、セキュリティ評価者の訓練や習熟度の評価のための参照資料としても使えるでしょう。

4.3 Artificial Intelligence Assessment Techniques

原本 PDF p.17

4.3 人工知能による評価技術

The field of Artificial Intelligence (AI) involves the design and implementation of systems that exhibit capabilities of the human mind, such as reasoning, knowledge, perception, planning, learning, and communication. AI encompasses a number of sub-disciplines including machine learning, constraint satisfaction, search, agents and multi-agent systems, reasoning, and natural language engineering and processing. While the use of AI has met with both successes and defeats, its application in aspects of security metrics might prove beneficial, particularly as a means for reducing subjectivity and human involvement in performing security assessments.

原本 PDF p.17

人工知能（AI）の分野は、推論、知識、知覚、計画、学習、コミュニケーションなど、人間の知性の能力を示すシステムの設計と実装に関わります。AI には、機械学習、制約充足、探索、エージェントとマルチエージェントシステム、推論、自然言語工学・処理などの、多数の下位分野が含まれます。AI の利用には成功も失敗もありましたが、セキュリティメトリクスの側面への応用は、特にセキュリティ評価の実施における主観性と人間の関与を減らす手段として、有益であると判明するかもしれません。

The research goal is to identify areas of security evaluations that could be performed using AI or AI-assisted techniques and demonstrate their use. Dealing with uncertainty and inconsistency has been a part of AI from its origins. More recently, AI systems are beginning to emerge that can independently formulate, refine, and test hypotheses from observed data to uncover fundamental properties [Fig09]. Technologies for managing uncertainty and inconsistency have already been used in areas such as the ranking algorithms used in web search engines and are being applied to the broader area of homeland security [Che05]. The expectation is that AI technologies can play a similarly important role in the context of security assessments.

原本 PDF p.17

研究の目標は、AI または AI 支援技術を使って実施できるセキュリティ評価の領域を特定し、その利用を実証することです。不確かさと不整合への対処は、AI の黎明期から AI の一部でした。最近では、観測データから仮説を独立に立案、洗練、検証して、基本的な特性を明らかにできる AI システムが現れ始めています [Fig09]。不確かさと不整合を管理する技術は、Web 検索エンジンで使われるランキングアルゴリズムなどの分野で既に使われており、より広い国土安全保障の分野にも適用されつつあります [Che05]。AI 技術は、セキュリティ評価の文脈でも、同様に重要な役割を果たせると期待されます。

For example, fuzzy logic is a superset of conventional logic that has been extended to handle the uncertainty in data. Fuzzy logic is useful in situations where it is difficult to make a precise statement about system behavior and has been applied successfully to the area of risk management [Don07, Mcg07, Sha03]. In these applications, qualitative risk descriptors, such as High, Medium, and Low, are able to be assigned to a range of values and calibrated as continuous quantitative input. In one case, fuzzy logic was used to assess the relative risk associated with computer network assets by ranking vulnerabilities with regard to the potential risk exposures of assets and networks [Don07]. In another case, using fuzzy logic provided risk analysts more information than qualitative approaches for ranking risks, to help them more effectively manage operational risks [Sha03].

原本 PDF p.17

たとえば、ファジー論理は、データの不確かさを扱えるように拡張された、従来の論理の上位集合です。ファジー論理は、システムの動作について正確な記述を行うことが難しい状況で有用であり、リスク管理の分野に成功裏に適用されてきました [Don07, Mcg07, Sha03]。これらの適用では、高・中・低などの定性的なリスク記述子を、値の範囲に割り当て、連続的な定量入力として較正できます。ある事例では、資産とネットワークの潜在的なリスクエクスポージャーに関して脆弱性を順位づけすることで、コンピュータネットワーク資産に関連する相対リスクを評価するために、ファジー論理が使われました [Don07]。別の事例では、ファジー論理を使うと、リスク分析者は、リスクの順位づけについて、定性的な手法よりも多くの情報を得られ、運用リスクをより効果的に管理するうえで助けになりました [Sha03]。

4.4 Practicable Concrete Measurement Methods

原本 PDF p.18

4.4 実行可能な具体的測定方法

The current practice of security assessment, best illustrated by lower level evaluations under the Common Criteria, emphasizes the soundness of the evaluation evidence of the design and the process used in developing a product over the soundness of the product implementation. The rationale is that without a correct and effective design and development process, a correct and effective implementation is not possible. While this is true, the emphasis on design and process evidence versus actual product software largely overshadows practical security concerns involving the implementation and deployment of operational systems. The research goal is to devise methods of measurement that address vulnerabilities occurring in implementation and deployment and complementing existing security assessment practices that emphasize design and development process evidence. The intent is to be able to detect vulnerabilities that otherwise would escape detection.

原本 PDF p.18

セキュリティ評価の現在の実務は、Common Criteria の下位レベルの評価に最もよく表れていますが、製品実装の健全性よりも、製品の開発に用いられた設計とプロセスに関する評価証拠の健全性を重視しています。その根拠は、正しく有効な設計・開発プロセスがなければ、正しく有効な実装は不可能であるというものです。これは事実ですが、実際の製品ソフトウェアよりも設計とプロセスの証拠に重点を置くことで、運用システムの実装と展開に関わる実際的なセキュリティ上の懸念は、大部分が影に隠れています。研究の目標は、実装と展開で生じる脆弱性を扱うとともに、設計・開発プロセスの証拠を重視する既存のセキュリティ評価の実務を補完する測定方法を考案することです。意図は、そうでなければ検出を逃れる脆弱性を検出できるようにすることです。

Code analysis has been a traditional way to examine code automatically and identify software problems that stem from violations in standard coding practices. Code analysis tools that are capable of identifying different types of potentially exploitable vulnerabilities have also been developed for security [Cha06, Mic06]. They provide a good example of one type of concrete measurement method possible, which is reproducible, repeatable, relevant, and timely. Although such security analysis tools provide highly useful results, they detect vulnerabilities incompletely and generate significant numbers of false positives, allowing room for improvement (e.g., [Sch05, Kir06]).

原本 PDF p.18

コード分析は、コードを自動的に調べて、標準的なコーディング実務への違反に起因するソフトウェアの問題を特定する、従来からの方法です。悪用される可能性のあるさまざまな種類の脆弱性を特定できるコード分析ツールも、セキュリティ向けに開発されています [Cha06, Mic06]。これらは、再現性、反復性、関連性、適時性を備えた、可能な具体的測定方法の一種のよい例になっています。このようなセキュリティ分析ツールは非常に有用な結果を提供しますが、脆弱性の検出は不完全で、かなりの数の誤検知を生成するため、改善の余地があります（例: [Sch05, Kir06]）。

Relatively little is known about software behavior or misbehavior after deployment [Bow02, Lib04]. Traditional means of feedback such as error or vulnerability reporting often are imprecise, contain inaccuracies, and involve delay, making it difficult to form a complete picture representative of the situation. Cooperative Bug Isolation (CBI) is an innovative technique that uses software instrumentation and sparse random sampling to gather information from the actual operation of deployed software [Lib04]. Algorithms have been developed for finding and fixing software errors based on statistical analysis of sparse feedback data. While developed for debugging purposes, the potential seemingly exists to extend the framework as a method of measurement for security through selective predicate instrumentation.

原本 PDF p.18

展開後のソフトウェアの動作や不適切な動作については、比較的わずかなことしかわかっていません [Bow02, Lib04]。エラーや脆弱性の報告など、従来のフィードバックの手段は、不正確であったり、誤りを含んでいたり、遅れを伴ったりすることが多く、状況を代表する完全な全体像を形成することが困難です。Cooperative Bug Isolation（CBI）は、ソフトウェアのインストルメンテーションと疎なランダムサンプリングを使って、展開されたソフトウェアの実際の動作から情報を収集する、革新的な技術です [Lib04]。疎なフィードバックデータの統計的分析に基づいて、ソフトウェアのエラーを見つけて修正するためのアルゴリズムが開発されています。デバッグを目的として開発されたものですが、選択的な述語のインストルメンテーションを通じて、この枠組みをセキュリティの測定方法に拡張できる可能性があるように思われます。

Various forms of black box security testing offer another example of a possible type of concrete measurement method. For example, fuzzing is a type of fault injection technique that involves sending various types of pseudorandom data to available interfaces to discover unknown flaws present in programs and systems [Jur06]. Fuzzing techniques have been shown to be an effective means for detecting security vulnerabilities. Robustness testing is a closely related technique, which involves determining how well a software system or component functions when subjected to invalid inputs or other conditions that induce stress on the implementation. Incorrect behaviors exhibited under stressful conditions can often lead to potential security exploits such as denial of service [Kak01, Ron02].

原本 PDF p.18

ブラックボックスのセキュリティ試験のさまざまな形式は、可能な具体的測定方法の種類のもう一つの例になります。たとえば、ファジングは、利用可能なインタフェースにさまざまな種類の疑似乱数データを送り、プログラムやシステムに存在する未知の欠陥を発見する、フォールトインジェクション技術の一種です [Jur06]。ファジング技術は、セキュリティ脆弱性を検出するための効果的な手段であることが示されています。堅牢性試験は、これと密接に関連する技術で、不正な入力や、実装にストレスを与えるその他の条件にさらしたときに、ソフトウェアシステムや構成要素がどの程度うまく機能するかを判定するものです。ストレスのかかる条件下で示される誤った動作は、サービス拒否など、潜在的なセキュリティ上の悪用につながることがよくあります [Kak01, Ron02]。

4.5 Intrinsically Measurable Components

原本 PDF p.19

4.5 本質的に測定可能な構成要素

Development of computing components that are inherently attuned to measurement would be a significant improvement in the state of the art of security metrics. The idea is to build components that clearly exhibit properties that matter to security. The research goal lies mainly on issues of mechanism and component design that facilitate or promote security measurement. For example, preparing strength of mechanism arguments in conjunction with the design and development of a security-enforcing component might be one method. Lower and upper bounds could be established, similar to the way performance bounds are calculated for sorting, matching, and other essential algorithms used in computing.

原本 PDF p.19

本質的に測定に適した計算構成要素を開発することは、セキュリティメトリクスの技術水準の大きな向上になるでしょう。その考え方は、セキュリティにとって重要な特性を明確に示す構成要素を構築することです。研究の目標は、主に、セキュリティ測定を容易にする、または促進する、機構と構成要素の設計の問題にあります。たとえば、セキュリティを実施する構成要素の設計と開発に合わせて、機構の強度を裏付ける論拠を構築することも一つの方法かもしれません。計算に使われるソート、マッチングなどの基本的なアルゴリズムの性能の限界を計算する方法と同様に、下限と上限を確立できるでしょう。

Cryptographic mechanisms are an area where research results exist and bounds on the effort required to breach components could be determined, under specific assumptions. Extending this type of analysis to trust mechanisms is a more challenging problem, but one with significant benefits, if achieved. Components that rely on certain surety mechanisms, such as authentication modules designed for passwords or biometric modules for fingerprints, lend themselves to certain types of strength analysis (e.g., password space size [Lee08]), and results already exist that could be applied. Finally, techniques for strength analysis might also be drawn from physical security, such as metrics used by industry to evaluate safe and vault security and identify weaknesses leading to failure [Bla04].

原本 PDF p.19

暗号機構は、研究結果が存在し、特定の仮定の下で、構成要素を破るために必要な労力の限界を判定できる分野です。この種の分析を信頼機構に拡張することは、より難しい問題ですが、達成できれば大きな利益があります。パスワード用に設計された認証モジュールや指紋用の生体認証モジュールのように、特定の確実性機構に依存する構成要素は、特定の種類の強度分析（例: パスワード空間の大きさ [Lee08]）に適しており、適用できる結果が既に存在します。最後に、強度分析の技術は、金庫や保管庫のセキュリティを評価し、失敗につながる弱点を特定するために業界で使われているメトリクス [Bla04] など、物理セキュリティから得られる可能性もあります。

Another possible area involves the application of evaluation criteria to system design. One possibility is to determine whether a methodology can be formulated for stipulating how to compose individually evaluated components of systems, such that the security of the overall system is ensured. The Trusted Network Interpretation (TNI) served this purpose for the TCSEC, but it was tied to Department of Defense security policies and a small standardized subset of security profiles. Attempting to devise a similar type of methodology for the Common Criteria would be more difficult because of the vast range of protection profiles that are able to be specified and which already exist. Nevertheless, it may be possible to narrow that scope to a definable composable subset through the systematic application of rules, principles, and logic.

原本 PDF p.19

もう一つの考えられる分野は、評価基準のシステム設計への適用に関わります。一つの可能性は、システム全体のセキュリティが確保されるように、個別に評価された構成要素をどのように合成するかを定める方法論を策定できるかどうかを判断することです。Trusted Network Interpretation（TNI）は TCSEC に対してこの目的を果たしましたが、これは国防総省のセキュリティポリシーと、標準化された小規模なセキュリティプロファイルの部分集合に結び付いていました。Common Criteria について同様の種類の方法論を考案しようとすることは、指定可能で、かつ既に存在する保護プロファイルの範囲が非常に広いため、より困難になります。それでも、規則、原則、論理を体系的に適用することで、その範囲を、定義可能な合成可能な部分集合に絞り込める可能性があります。
