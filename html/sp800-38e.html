3 Introduction

原本 PDF p.9

3 はじめに

The XTS-AES algorithm is a mode of operation of the Advanced Encryption Standard (AES) [1] algorithm. The Security in Storage Working Group (SISWG) of the P1619 Task Group of the Institute of Electrical and Electronics Engineers, Inc (IEEE) developed and specified XTS-AES in IEEE Std. 1619-2007 [2]. This Recommendation approves the XTS-AES mode as specified in that standard, subject to one additional requirement on the lengths of the data units, which is discussed in Section 4 below.

原本 PDF p.9

XTS-AESアルゴリズムは、高度暗号化標準（AES）[1]アルゴリズムの利用モードである。米国電気電子学会（IEEE）のP1619タスクグループに属するSecurity in Storage Working Group（SISWG）が、IEEE Std. 1619-2007 [2]でXTS-AESを開発し、規定した。本勧告は、同規格に規定されたXTS-AESモードを承認する。ただし、データユニットの長さに関する追加要件を1つ課す。この要件については、以下の第4節で説明する。

The XTS-AES mode was designed for the cryptographic protection of data on storage devices that use of fixed length “data units,” as defined in Ref. [2]. Note that other approved cryptographic algorithms continue to be approved for such devices. The XTS-AES mode was not designed for other purposes, such as the encryption of data in transit.

原本 PDF p.9

XTS-AESモードは、文献[2]で定義される固定長の「データユニット」を使用するストレージデバイス上のデータを暗号学的に保護するために設計された。このようなデバイスについては、他の承認済み暗号アルゴリズムも引き続き承認されていることに留意されたい。XTS-AESモードは、転送中のデータの暗号化など、他の目的のためには設計されていない。

The XTS-AES mode is an instantiation of Rogaway’s XEX (XOR Encrypt XOR) tweakable block cipher [3], supplemented with a method called “ciphertext stealing” to extend the domain of possible input data strings. In particular, XEX can only encrypt sequences of complete blocks, i.e., any data string that is an integer multiple of 128 bits; whereas for XTS-AES, the data string may also consist of one or more complete blocks followed by a single, non-empty partial block. (The acronym XTS stands for the XEX Tweakable Block Cipher with Ciphertext Stealing).

原本 PDF p.9

XTS-AESモードは、RogawayのXEX（XOR Encrypt XOR）調整可能ブロック暗号[3]を具体化したものであり、「暗号文窃取」と呼ばれる方法を追加して、入力データ文字列として可能な範囲を拡張する。特に、XEXで暗号化できるのは完全なブロックの列、すなわち長さが128ビットの整数倍であるデータ文字列に限られる。一方、XTS-AESでは、データ文字列は1つ以上の完全なブロックの後に、空でない部分ブロックが1つ続く構成でもよい。（略称XTSは、XEX Tweakable Block Cipher with Ciphertext Stealingを表す。）

The specification of the ciphertext stealing method in Ref.[2] includes an ordering convention for the final complete block and partial block of the encrypted data string. A different convention, in which the order is swapped, may be desirable in some cases. The specification in Ref.[2] provides flexibility in the physical location of these elements, as long as interoperability is not compromised, as discussed in Section 5.

原本 PDF p.10

文献[2]における暗号文窃取方式の仕様には、暗号化データ文字列の最後の完全ブロックと部分ブロックの順序規約が含まれている。順序を入れ替える別の規約が望ましい場合もある。第5節で説明するように、相互運用性が損なわれない限り、文献[2]の仕様はこれらの要素の物理的な配置に柔軟性を認めている。

The XTS-AES mode provides confidentiality for the protected data. Authentication is not provided, because the P1619 Task Group designed XTS-AES to provide encryption without data expansion, so alternative cryptographic methods that incorporate an authentication tag are precluded. In the absence of authentication or access control, XTS-AES provides more protection than the other approved confidentiality-only modes against unauthorized manipulation of the encrypted data.

原本 PDF p.10

XTS-AESモードは、保護対象データの機密性を提供する。認証は提供されない。これは、P1619タスクグループがデータ拡張なしの暗号化を提供するようXTS-AESを設計したためであり、そのため認証タグを組み込む別の暗号方式は使用できない。認証またはアクセス制御がない場合、暗号化データの不正な改変に対して、XTS-AESは他の承認済みの機密性のみを提供するモードより高い保護を提供する。

Annex D of Ref.[2] discusses in detail the design choices for XTS, including the resistance to manipulation of the encrypted data, and their ramifications for the incorporation of XTS-AES into an information system. Prospective implementers of XTS-AES should consider this information carefully to ensure that XTS-AES is an appropriate solution for a given threat model.

原本 PDF p.10

文献[2]の附属書Dでは、暗号化データの改変に対する耐性を含め、XTSの設計上の選択と、情報システムへのXTS-AESの組み込みに伴う影響について詳しく論じている。XTS-AESの導入を検討する者は、特定の脅威モデルにXTS-AESが適切な解決策であることを確認するため、この情報を慎重に検討するべきである。

4 Conformance

原本 PDF p.10

4 適合性

An instance of an XTS-AES implementation is defined by the following three elements, as specified in Ref. [2]:

原本 PDF p.10

文献[2]で規定されるXTS-AES実装のインスタンスは、次の3つの要素によって定義される。

1) a secret key,
2) a single, fixed length for the data units that the key protects,
3) an implementation of the XTS-AES-Enc procedure or the XTS-AES-Dec procedure, or both,
for the key and the length of the data units.

原本 PDF p.10

1) 秘密鍵、
2) その鍵で保護するデータユニットの単一の固定長、
3) XTS-AES-Enc手順またはXTS-AES-Dec手順、あるいはその両方の実装、
対象の鍵およびデータユニット長に対するもの。

The length of the data unit for any instance of an implementation of XTS-AES shall not exceed 220 AES blocks. Note that Subclause 5.1 of Ref.[2] recommends this limit but does not require it.

原本 PDF p.10

XTS-AES実装の任意のインスタンスにおけるデータユニットの長さは、220個のAESブロックを超えてはならない。文献[2]の細則5.1はこの上限を推奨しているが、必須とはしていない点に留意すること。

An implementation of the XTS-AES encryption mode may claim conformance with this Recommendation if every supported instance satisfies this length requirement for a data unit, in addition to all of the requirements in Clauses 1-6 of Ref. [2].

原本 PDF p.10

XTS-AES暗号化モードの実装は、サポートするすべてのインスタンスが、文献[2]の箇条1～6のすべての要件に加えて、データユニットのこの長さ要件を満たす場合、本勧告への適合を主張してもよい。

Key management is important for XTS-AES, as for any keyed cryptographic algorithm, but the representation of a key backup structure in the Extensible Markup Language (XML) that is specified in Clause 7 of Ref. [2] is outside the scope of this Recommendation.

原本 PDF p.10

鍵管理は、鍵を用いる他の暗号アルゴリズムと同様にXTS-AESにとって重要であるが、文献[2]の箇条7で規定されるXML（Extensible Markup Language）形式の鍵バックアップ構造の表現は、本勧告の適用範囲外である。

Consistent with the 220 block limit for a data unit, an implementation of XTS-AES may further restrict the length of the data units for any key. For example, an implementation may support only data units that are sequences of complete blocks. In this case, the ciphertext stealing components in the implementations of the XTS-AES-Enc and the XTS-AES-Dec procedures would be unnecessary, and these procedures essentially would be reduced to the XTS-AES-blockEnc and the XTS-AES-blockDec procedures, as specified in Ref. [2].

原本 PDF p.10

データユニットに対する220ブロックの上限と整合する範囲で、XTS-AES実装は任意の鍵についてデータユニット長をさらに制限してもよい。たとえば、完全ブロックの列であるデータユニットだけをサポートしてもよい。この場合、XTS-AES-Enc手順およびXTS-AES-Dec手順の実装における暗号文窃取部分は不要となり、これらの手順は実質的に、文献[2]で規定されるXTS-AES-blockEnc手順およびXTS-AES-blockDec手順に縮約される。

Similarly, an implementation may restrict its support to either the 256-bit key size (for XTS-AES-128) or the 512-bit key size (for XTS-AES-256).

原本 PDF p.11

同様に、実装は256ビット鍵サイズ（XTS-AES-128の場合）または512ビット鍵サイズ（XTS-AES-256の場合）のいずれかだけをサポートするよう制限してもよい。

Restrictions on the supported lengths of the key or the data units may affect interoperability with other implementations.

原本 PDF p.11

サポートする鍵長またはデータユニット長に対する制限は、他の実装との相互運用性に影響を与える可能性がある。

Conformance testing for implementations of XTS-AES is conducted within the framework of the Cryptographic Module Validation Program (CMVP), a joint effort of NIST and the Communications Security Establishment Canada.

原本 PDF p.11

XTS-AES実装の適合性試験は、NISTとカナダ通信保安局（Communications Security Establishment Canada）の共同事業である暗号モジュール検証プログラム（CMVP）の枠組みで実施される。

5 Ordering Convention for the Ciphertext Stealing Case

原本 PDF p.11

5 暗号文窃取の場合の順序規約

If the length of the data units for an instance of XTS-AES is not an integral multiple of the block size, then the specification in Ref. [2] denotes the unencrypted form of a data unit, i.e., the plaintext, as a sequence of complete blocks, \(P_0, P_1, \ldots P_{m-1}\), followed by a single, non-empty partial block \(P_m\), where \(m\) is a positive integer determined by the length of the data unit.

原本 PDF p.11

XTS-AESのインスタンスにおけるデータユニット長がブロックサイズの整数倍でない場合、文献[2]の仕様では、データユニットの暗号化前の形式、すなわち平文を、完全ブロックの列\(P_0, P_1, \ldots P_{m-1}\)に続いて、空でない部分ブロック\(P_m\)が1つあるものとして表す。ここで\(m\)は、データユニットの長さによって決まる正の整数である。

In this case, the encrypted form of the data unit, i.e., the ciphertext, has the same structure: a sequence of complete blocks, denoted \(C_0, C_1, \ldots C_{m-1}\), followed by a single, non-empty partial block \(C_m\), whose length is the same as the length of \(P_m\).

原本 PDF p.11

この場合、データユニットの暗号化後の形式、すなわち暗号文も同じ構造を持つ。\(C_0, C_1, \ldots C_{m-1}\)と表す完全ブロックの列の後に、空でない部分ブロック\(C_m\)が1つ続く。その長さは\(P_m\)の長さと同じである。

For some implementations, an alternative ordering convention, in which the positions of \(C_{m-1}\) and \(C_m\) are swapped, may be desirable for the physical storage of the bits, because that ordering corresponds more closely with the generation of the ciphertext. In particular, \(C_m\) is the truncation of a block that is derived from \(P_{m-1}\), and \(C_{m-1}\) is derived from \(P_m\), concatenated with the discarded bits from the truncation.

原本 PDF p.11

一部の実装では、ビットの物理的な格納のため、\(C_{m-1}\)と\(C_m\)の位置を入れ替える別の順序規約が望ましい場合がある。これは、その順序が暗号文の生成過程により近いためである。特に、\(C_m\)は\(P_{m-1}\)から導出されたブロックを切り詰めたものであり、\(C_{m-1}\)は、\(P_m\)に切り詰め時に破棄されたビットを連結したものから導出される。

Subclause 5.1 of [2] indicates that an implementation of XTS-AES should include a mapping between the pairs of indices that define the blocks (and possibly a single partial block) of a data unit and their physical location in the storage device, but that the mapping itself is outside the scope of the standard.

原本 PDF p.11

文献[2]の細則5.1では、XTS-AES実装は、データユニットのブロック（および場合によっては1つの部分ブロック）を定義するインデックスの組と、ストレージデバイス上のそれらの物理的位置との対応付けを含めるべきであるとしている。ただし、その対応付け自体は規格の適用範囲外である。

Thus, if every external interface to the data retrieves the data in a manner that is consistent with the ordering specified in Ref [2], then the last block and the partial block may be stored in any convenient locations in the storage device. In other words, if necessary, a mechanism for swapping the last complete block and the partial block could be built into the interface.

原本 PDF p.11

したがって、データへのすべての外部インターフェースが、文献[2]に規定された順序と整合する方法でデータを取得するなら、最後のブロックと部分ブロックは、ストレージデバイス上の都合のよい任意の位置に格納してもよい。言い換えれば、必要に応じて、最後の完全ブロックと部分ブロックを入れ替える機構をインターフェースに組み込むことができる。
