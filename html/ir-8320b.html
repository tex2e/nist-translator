Abstract

原本 PDF p.4

概要

In today’s cloud data centers and edge computing, attack surfaces have significantly increased, cyber attacks are industrialized, and most security control implementations are not coherent or consistent. The foundation of any data center or edge computing security strategy should be securing the platform on which data and workloads will be executed and accessed. The physical platform represents the foundation for any layered security approach and provides the initial protections to help ensure that higher-layer security controls can be trusted. This report explains an approach based on hardware-enabled security techniques and technologies for safeguarding container deployments in multi-tenant cloud environments. It also describes a prototype implementation of the approach intended to be a blueprint or template for the general security community.

原本 PDF p.4

今日のクラウドデータセンターやエッジコンピューティングでは、攻撃対象領域が大幅に拡大し、サイバー攻撃は産業化され、ほとんどのセキュリティ対策の実装は一貫性や整合性を欠いています。データセンターやエッジコンピューティングのセキュリティ戦略の基盤となるべきは、データやワークロードが実行・アクセスされるプラットフォームを保護することです。物理プラットフォームは、あらゆる多層的セキュリティアプローチの基盤であり、上位層のセキュリティ対策が信頼できることを保証するための初期保護策を提供します。本報告書は、マルチテナントのクラウド環境でコンテナーのデプロイメントを保護するための、ハードウェアによるセキュリティ技法および技術に基づくアプローチを説明します。また、このアプローチのプロトタイプ実装についても説明します。このプロトタイプ実装は、一般のセキュリティコミュニティにとってのブループリントまたはテンプレートとなることを意図しています。

2.1 Objective

原本 PDF p.10

2.1 目標

There are security and privacy concerns with allowing unrestricted container deployment orchestration. A common desire is to only use cloud servers physically located within the same country as the organization, or physically located in the same country as the origin of the information. Whenever multiple container deployments are present on a single cloud server, there is a need to segregate those deployments from each other so that they do not interfere with each other, gain access to each other’s sensitive data, or otherwise compromise the security or privacy of the containers. NIST IR 8320A, Hardware-Enabled Security: Container Platform Security Prototype [1] provides an overview of challenges organizations may face when using cloud-based container workloads, as well as techniques to improve the security of cloud computing and accelerate the adoption of cloud computing technologies by establishing an automated hardware root-of-trust method for enforcing and monitoring platform integrity and geolocation restrictions for cloud servers.

原本 PDF p.10

コンテナーのデプロイメントのオーケストレーションを無制限に許可することには、セキュリティおよびプライバシー上の懸念があります。組織と同じ国、または情報の発生元と同じ国に物理的に所在するクラウドサーバーだけを使用したいという要望はよくあります。1 台のクラウドサーバー上に複数のコンテナーデプロイメントが存在する場合は常に、それらが互いに干渉したり、互いの機微なデータにアクセスしたり、その他の形でコンテナーのセキュリティやプライバシーを侵害したりしないよう、デプロイメント同士を分離する必要があります。NIST IR 8320A『Hardware-Enabled Security: Container Platform Security Prototype』[1] は、クラウドベースのコンテナーワークロードを使用する際に組織が直面しうる課題の概要を示すとともに、クラウドサーバーのプラットフォームの完全性と地理的位置の制限を強制および監視する、自動化されたハードウェアルートオブトラストの手法を確立することで、クラウドコンピューティングのセキュリティを向上させ、クラウドコンピューティング技術の導入を加速させる技法を示しています。

The motivation behind this use case is to build upon the stages of NIST IR 8320A and implement additional techniques that leverage hardware roots of trust in server platforms. The integrity and location data of each host are leveraged in the orchestration and protection of workloads, as well as providing workloads access to specific data. Workload orchestration can ensure that containers are instantiated only on server platforms that meet trustworthiness requirements and are in acceptable locations. Orchestration can also involve initial encryption of container images and releasing the decryption keys only to trusted servers. Additionally, the workloads themselves can be assigned identities based on these trusted attributes of the physical servers they reside on and be granted access to sensitive information based on their identities.

原本 PDF p.10

原本 PDF p.17

6.1 ソリューションの概要

Consumers who place their workloads in the cloud or the edge are typically forced to accept that their workloads are secured by their service providers without insight or knowledge as to what security mechanisms are in place. The ability for end users to encrypt their workload images can provide at-rest cryptographic isolation to help protect consumer data and intellectual property.

原本 PDF p.17

When the runtime node service receives the launch request, it can detect that the image is encrypted and make a request to retrieve the decryption key. This request can be passed through an attestation service so that an internal trust evaluation for the platform can be performed. The key request is forwarded to the key broker with proof that the platform has been attested. The key broker can then verify the attested platform report and release the key back to the cloud service provider and node runtime services. At that time the node runtime can decrypt the image and proceed with the normal workload orchestration. The disk encryption kernel subsystem can provide at-rest encryption for the workload on the platform.

原本 PDF p.17

7.1 Solution Overview

原本 PDF p.19

7.1 ソリューションの概要

The majority of workloads running in the cloud need some access to data sources or other services. To do this, they must authenticate themselves using a password, API key, or certificate. Today, this is typically done through secrets. Even though secrets are designed to be stored securely (for example, encrypted at rest) by the orchestration, they can simply be mounted to an arbitrary container and read by anyone who has access to the namespace, including cloud administrators. Those knowing the secret can also access the sensitive data that needs to be protected. The problem with the secrets is that once they are stored, they are also available to administrators, cloud operators, or anyone else with access to the namespace, whether or not they are authorized to access the data that the secrets protect.

原本 PDF p.19

クラウドで稼働するワークロードの大半は、データソースやその他のサービスに何らかのアクセスを必要とします。そのためには、パスワード、API キー、または証明書を使用して自らを認証しなければなりません。現在、これは通常シークレットによって行われています。シークレットは、オーケストレーションによって安全に保管（たとえば保存時に暗号化）されるよう設計されていますが、任意のコンテナーにマウントするだけで、クラウド管理者を含む、その名前空間にアクセスできる誰でも読み取ることができます。シークレットを知っている人は、保護すべき機微なデータにもアクセスできます。シークレットの問題は、一度保管されると、そのシークレットが保護するデータへのアクセスが認可されているかどうかにかかわらず、管理者、クラウドオペレーター、またはその名前空間にアクセスできるその他の人も、そのシークレットを利用できることです。

Trust-based workload access to information protects sensitive data access by ensuring only attested services with specific location-based restrictions can access the secrets. This is done through the use of workload identity, which is composed of the trusted hardware identity data that has been fully attested, including the data center location and region, and various runtime measurements to identify the application. These measurements are securely signed by a service running on each worker node, using a chain of trust created during the secure bootstrapping of the environment, then continuously attested and validated. The bootstrapping of the environment requires configuring a secret store that runs a root Certificate Authority (CA), and installing an intermediate CA and token signing service on each worker node. Each worker node with the token signing service uses its hardware root of trust to protect its individual private key.

原本 PDF p.19

原本 PDF p.34

付録 D—Trusted Service Identity（TSI）

This section contains supplementary information describing all the required components and steps required to set up the prototype implementation for the Trusted Service Identity (TSI).

原本 PDF p.34

本節には、Trusted Service Identity（TSI）に関するプロトタイプ実装のセットアップに必要なすべてのコンポーネントと手順を説明する補足情報を記載しています。

D.1 TSI Overview

原本 PDF p.34

D.1 TSI の概要

TSI protects sensitive data access by ensuring only attested services with specific location-based restrictions can obtain credentials. This is done through the use of workload identity, composed of the trusted hardware identity data that has been fully attested by Intel TXT, including the data center location and region, and various runtime measurements like the image and cluster name, unique pod IDs, and namespace to identify the application. These measurements are securely signed by a service running on every hosting node, using a chain of trust created during the secure bootstrapping of the environment, then continuously attested and validated.

原本 PDF p.34

TSI は、場所に基づく特定の制限を満たす、アテステーション済みのサービスのみが認証情報を取得できるようにすることで、機微なデータへのアクセスを保護します。これは、ワークロードの識別情報を使用して行われます。ワークロードの識別情報は、データセンターの場所やリージョンを含め、Intel TXT によって完全にアテステーションされた信頼できるハードウェアの識別データと、アプリケーションを識別するための、イメージ名やクラスター名、一意の Pod ID、名前空間などのさまざまなランタイム計測値で構成されます。これらの計測値は、環境の安全なブートストラップ時に作成された信頼の連鎖を使用して、すべてのホスティングノードで稼働するサービスによって安全に署名され、その後継続的にアテステーションおよび検証されます。

Every container that requires a secret for accessing sensitive data is assigned a short-lived measured identity, in the form of a JSON Web Token (JWT) token, that is signed with the root of trust by the attested process. This measured identity is a form of an ephemeral digital biometric with a short time to live.

原本 PDF p.34

機微なデータにアクセスするためのシークレットを必要とするすべてのコンテナーには、アテステーションされたプロセスがルートオブトラストで署名した、JSON Web Token（JWT）トークン形式の、有効期間の短い計測済み識別情報が割り当てられます。この計測済み識別情報は、存続時間の短い一時的なデジタル生体情報の一形態です。

In this implementation, there is a Kubernetes cluster running on OpenShift, extended with TSI, where each node has an intermediate CA signed by the root CA during the secure bootstrapping of the cluster.

原本 PDF p.34

この実装では、OpenShift 上で稼働し TSI で拡張された Kubernetes クラスターがあり、各ノードは、クラスターの安全なブートストラップ時にルート CA によって署名された中間 CA を持ちます。

During this bootstrapping, the installation process obtains an attestation report (Security Assertion Markup Language [SAML]) from the Attestation Server for every worker node. This report is checked to verify if all the components are trusted (OS, platform, and software), and the bootstrapping process retrieves worker identity fields from the asset tag of this report. Each worker node also has a JWT Signing Service (JSS) that contains a signing authority that uses the hardware TPM to protect its individual private key.

原本 PDF p.34

このブートストラップの間に、インストールプロセスは、すべてのワーカーノードについてアテステーションサーバーからアテステーションレポート（Security Assertion Markup Language [SAML]）を取得します。このレポートは、すべてのコンポーネント（OS、プラットフォーム、ソフトウェア）が信頼できるかを検証するために確認され、ブートストラッププロセスは、このレポートのアセットタグからワーカーの識別情報フィールドを取得します。各ワーカーノードには JWT 署名サービス（JSS）もあり、これはハードウェア TPM を使用してそれぞれの秘密鍵を保護する署名機関を含んでいます。

The root CA is securely stored in a vault, which is extended with the TSI Authentication Vault plugin.

原本 PDF p.34

ルート CA は、TSI Authentication Vault プラグインで拡張されたボールトに安全に保管されます。

D.2 TSI のインストールと設定

TSI requires an attestation process to accurately define the identity of the worker nodes hosting the application containers. In this implementation, TSI relies on the ISecL server that has been deployed to provide the identity of the worker nodes. Steps detailing the integration of TSI with ISecL can be found here: https://github.com/IBM/trusted-service-identity/blob/intel-asset/README.md#attestation.

原本 PDF p.34

TSI には、アプリケーションコンテナーをホストするワーカーノードの識別情報を正確に定義するためのアテステーションプロセスが必要です。この実装では、TSI は、ワーカーノードの識別情報を提供するためにデプロイされた ISecL サーバーに依拠します。TSI と ISecL の統合手順の詳細は次の場所にあります: https://github.com/IBM/trusted-service-identity/blob/intel-asset/README.md#attestation 。

This process requires two independent phases:

原本 PDF p.34

•Asset Registration with Intel Verification Server – The trusted bootstrapping process responsible for installing the environment must properly set the identity attributes of every worker node. As a result, they are included in the SAML attestation report that also includes all the attestation results (OS, platform, software trusted). This process was performed in the steps outlined in Appendix A.

原本 PDF p.34

•Intel 検証サーバーへのアセット登録 – 環境のインストールを担うトラステッドなブートストラッププロセスは、すべてのワーカーノードの識別属性を適切に設定しなければなりません。アセットタグの形式をとるこれらの識別値は、ホスト上の対応する TPM に安全に保管されます。その結果、これらは、すべてのアテステーション結果（OS、プラットフォーム、ソフトウェアが信頼できる）も含む SAML アテステーションレポートに含まれます。このプロセスは、付録 A に示した手順で実施しました。

For details outlining the suggested configuration changes, visit https://github.com/IBM/trusted-service-identity/blob/intel-asset/README.md#attestation.

The claims included here represent the measured identity of the application. The hd-trusted value determines whether all the attested elements are trusted.

There is also a token expiration timestamp, typically set to one minute, to make these tokens ephemeral and short-lived, protecting the security from leaking. These are the runtime measurements that represent the identity of the application, signed with the root of trust, and used for evaluation against policies controlling the secrets.

The secrets stored in the Vault are protected by policies.
