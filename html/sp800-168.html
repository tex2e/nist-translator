1.1 Purpose and Scope

1.1 目的と適用範囲

Approximate matching is a promising technology designed to identify similarities between two digital artifacts. It is used to find objects that resemble each other or to find objects that are contained in another object. This can be very useful for filtering data for security monitoring, digital forensics, or other applications. The purpose of this document is to provide a definition and terminology to describe approximate matching in order to promote discussion, research, tool development and tool acquisition. Approximate matching has the potential to provide valuable filtering in a world inundated with information, but the technique is not widely used. The goal of the document is to provide infrastructure to support advances in approximate matching and its use in forensics and security.

2. 定義と用語

Approximate matching is a generic term describing any technique designed to identify similarities between two digital artifacts. In this context, an artifact (or an object) is defined as an arbitrary byte sequence, such as a file, which has some meaningful interpretation.

原本 PDF p.9

近似マッチングとは、2つのデジタル成果物間の類似性を特定するために設計されたあらゆる手法を指す一般用語である。この文脈で成果物（またはオブジェクト）とは、ファイルのように、何らかの意味のある解釈が可能な任意のバイト列と定義される。

Different approximate matching methods may operate at different levels of abstraction. At the lowest level, generic techniques may detect the presence of common byte sequences (substrings) without any attempt to interpret the artifacts. At higher levels, approximate matching can incorporate more abstract analysis. In general lower level methods are expected to be faster and more generic in their applicability, whereas higher level methods are typically more targeted and require more processing.

原本 PDF p.9

近似マッチングの手法は、手法によって異なる抽象度で動作することがある。最も低いレベルでは、汎用的な手法が、成果物を解釈しようとすることなく、共通のバイト列（部分文字列）の存在を検出することがある。より高いレベルでは、近似マッチングに、より抽象的な分析を取り入れることができる。一般に、低レベルの手法はより高速で適用範囲もより汎用的であると期待され、一方、高レベルの手法は通常、より対象を絞ったものであり、より多くの処理を必要とする。

One common approach in security and forensic analysis is to find identical objects using cryptographic hashing. Approximate matching can be viewed as a generalization of that idea in that, instead of providing a yes/no {0, 1} answer to a comparison, it provides a range of outcomes, [0, 1], with the result interpreted as a measure of similarity.

原本 PDF p.9

セキュリティ分析やフォレンジック分析では、暗号学的ハッシュを使って同一のオブジェクトを見つける方法が一般的である。近似マッチングはこの考え方を一般化したものとみなせる。比較結果を yes/no の {0, 1} で示す代わりに、[0, 1] の範囲で示し、その値を類似性の尺度として解釈する。

2.1 Use cases

原本 PDF p.9

2.1 ユースケース

Broadly, there are two types of similarity queries that are of interest – resemblance and containment [1]. In the case of resemblance, we compare two similarly sized objects and interpret the result as a measure of the commonality between them; for example, two successive versions of a piece of code are likely to resemble each other substantially. When the compared objects differ in size significantly, such as a file and a whole-disk image, the test for commonality is interpreted as a containment query because it addresses the question of whether the large object contains the smaller one.

原本 PDF p.9

大別すると、関心の対象となる類似性クエリには、類似（resemblance）と包含（containment）の2種類がある[1]。類似クエリでは、サイズがほぼ同じ2つのオブジェクトを比較し、共通性の尺度として結果を解釈する。たとえば、あるコードの連続する2つのバージョンは、互いによく似ていると考えられる。ファイルとディスク全体のイメージのように、比較するオブジェクトのサイズが大きく異なる場合、共通性の検査は包含クエリとして解釈される。これは、大きなオブジェクトに小さなオブジェクトが含まれているかを問うものである。

An approximate matching algorithm should address at least one of the following problems (divided according to whether the query type is (R)esemblance or (C)ontainment) [2, 3]: Object similarity detection (R): identify related artifacts, e.g., different versions of a document. Cross correlation (R): identify artifacts that share a common object, e.g., a Microsoft Word document and a PDF document containing the same image, or other embedded object. Embedded object detection (C): identify a given object inside an artifact, e.g., an image within a compound document or an executable inside a memory capture. Fragment detection (C): identify the presence of traces/fragments of a known artifact, e.g., identify the presence of a file in a network stream based on individual packets. In most analytical scenarios, approximate matching is used to filter data in, or out, based on a known reference set. In security monitoring applications, approximate matching could potentially be used to blacklist known bad artifacts, and (by extension) anything closely resembling them. However, approximate matching is not nearly as useful when it comes to whitelisting artifacts as malicious content can often be quite similar to benign content; e.g., a backdoored ssh server would approximately match regular one.

原本 PDF p.9

近似マッチングアルゴリズムは、次の問題（クエリの種類が類似（R）か包含（C）かによって分類している）のうち少なくとも1つに対応すべきである[2, 3]。オブジェクト類似性の検出（R）：文書の異なるバージョンなど、関連する成果物を特定する。相互相関（R）：共通のオブジェクトを共有する成果物を特定する。たとえば、同じ画像またはその他の埋め込みオブジェクトを含むMicrosoft Word文書とPDF文書。埋め込みオブジェクトの検出（C）：複合文書内の画像やメモリキャプチャ内の実行可能ファイルなど、成果物の内部にある所与のオブジェクトを特定する。断片の検出（C）：既知の成果物の痕跡または断片の存在を特定する。たとえば、個々のパケットに基づいてネットワークストリーム内のファイルの存在を特定する。ほとんどの分析シナリオでは、近似マッチングは、既知の参照セットに基づいてデータを選び入れる、または除外するフィルタリングに使われる。セキュリティ監視の用途では、近似マッチングを使って、既知の悪意ある成果物、および（その延長として）それによく似たあらゆるものをブラックリストに登録できる可能性がある。しかし、悪意あるコンテンツは無害なコンテンツとかなり似ていることが多いため、成果物のホワイトリスト化に関しては、近似マッチングはそれほど有用ではない。たとえば、バックドアを仕込まれたsshサーバーは、通常のsshサーバーと近似マッチするであろう。

2.2 Terminology

原本 PDF p.10

2.2 用語

Although the common language definition of ‘similarity’ is sufficient to give an intuitive sense of the term, the multitude of ways in which two artifacts can be said to be similar poses a challenge when attempting to describe the purpose and behavior of approximate matching algorithms. For example, two strings ‘ababa’ and ‘cdcdc’ might be considered similar in that they both have five characters ranging over two alternating values, or they might be treated as dissimilar because they have no common characters. To resolve this ambiguity, approximate matching algorithms define similarity in terms of features that represent characteristics of the artifacts pertinent to the algorithm’s method of comparison.

原本 PDF p.10

「類似性」という語の一般的な意味は直感的な理解には十分だが、2つの成果物がどのような点で似ていると言えるかは多岐にわたるため、近似マッチングアルゴリズムの目的や動作を説明する際に課題となる。たとえば、文字列「ababa」と「cdcdc」は、どちらも2種類の値が交互に現れる5文字の列である点で似ているとも、共通の文字がない点で似ていないとも考えられる。この曖昧さを解消するため、近似マッチングアルゴリズムは、比較方法に関係する成果物の特性を表す特徴に基づいて類似性を定義する。

Features. The basic elements through which artifacts are compared. Comparison of two features always yields a binary {0, 1} outcome indicating a match or non-match; because features are defined as the most basic comparison unit that the algorithm considers, partial matches are not permitted. Generally, a feature can be any value derived from an artifact. Each approximate matching algorithm must define the structure of its features and the method by which they are derived. For example, an algorithm might define a feature as a (byte, offset) pair produced by reading the value of a byte and storing it along with the offset at which it was read. Feature set. The set of all features associated with a single artifact is its feature set. Each algorithm must include a criteria by which candidate features are selected for inclusion in this set. For example, an algorithm might select all the (byte, offset) pairs produced by reading every 16th byte in the artifact. Similarity. The similarity of two artifacts, as measured by a particular approximate matching algorithm, is defined as an increasing monotonic function of the number of matching features contained in their respective feature sets.

原本 PDF p.10

特徴（Features）。成果物を比較するための基本要素。2つの特徴を比較すると、常に、一致または不一致を示す二値の結果 {0, 1} が得られる。特徴はアルゴリズムが考慮する最も基本的な比較単位として定義されるため、部分一致は認められない。一般に、特徴は成果物から導出される任意の値であり得る。各近似マッチングアルゴリズムは、特徴の構造とその導出方法を定義しなければならない。たとえば、バイトの値を読み取り、その値を読み取った位置のオフセットとともに保存することで得られる（バイト、オフセット）の組を、特徴として定義するアルゴリズムが考えられる。特徴集合（Feature set）。1つの成果物に関連付けられたすべての特徴の集合が、その成果物の特徴集合である。各アルゴリズムは、この集合に含める候補特徴を選ぶ基準を含まなければならない。たとえば、成果物の16バイトごとに1バイトを読み取って得られるすべての（バイト、オフセット）の組を選ぶアルゴリズムが考えられる。類似性（Similarity）。特定の近似マッチングアルゴリズムで測定した2つの成果物の類似性は、それぞれの特徴集合に含まれる一致特徴の数の単調増加関数として定義される。

Based on the level of abstraction of the similarity analysis performed, approximate matching methods can be placed in one of three main categories [4]:

原本 PDF p.10

類似性分析の抽象度に基づき、近似マッチング手法は主に次の3種類に分類できる[4]。

Bytewise matching relies only on the sequences of bytes that make up a digital object, without reference to any structures within the data stream, or to any meaning the byte stream may have when appropriately interpreted. Such methods have the widest applicability as they can be applied to any piece of data; however, they also carry the implicit assumption that artifacts that humans perceive as similar have similar byte-level encodings. This assumption is not universally valid. Analyst expertise is necessary to evaluate the significance of a byte-level match. Syntactic matching uses internal structures present in digital objects. For ex ample, the structure of a TCP network packet is defined by an international standard and matching tools can make use of this structure during network packet analysis to match the source, destination or content of the packet. Syntax-sensitive similarity measurements are specific to a particular class of objects that share an encoding but require no interpretation of the content to produce meaningful results. Semantic matching uses contextual attributes of the digital object to interpret the artifact in a manner that more closely corresponds with human perceptual categories. For example, perceptual hashes allow the matching of visually similar images and are unconcerned with the low-level details of how the images are persistently stored. Semantic methods tend to provide the most specific results but also tend to be the most computationally expensive ones.

原本 PDF p.10

バイト単位のマッチングは、デジタルオブジェクトを構成するバイト列だけに依拠し、データストリーム内部のいかなる構造も、適切に解釈した場合にバイトストリームが持ち得るいかなる意味も参照しない。この種の手法はあらゆるデータに適用できるため、最も適用範囲が広い。ただし、人間が似ていると認識する成果物はバイトレベルの符号化も似ている、という暗黙の前提も伴う。この前提は常に成り立つわけではない。バイトレベルの一致の重要性を評価するには、分析者の専門知識が必要である。構文マッチングは、デジタルオブジェクトに存在する内部構造を利用する。たとえば、TCPネットワークパケットの構造は国際規格で定義されており、マッチングツールは、ネットワークパケット分析の際にこの構造を利用して、パケットの送信元、宛先、または内容を照合できる。構文に依存する類似性測定は、符号化を共有する特定の種類のオブジェクトに固有のものであるが、有意な結果を出すために内容の解釈を必要としない。意味マッチングは、デジタルオブジェクトの文脈的属性を使い、人間の知覚上の分類により近い形で成果物を解釈する。たとえば、知覚ハッシュは視覚的に似た画像の照合を可能にし、画像が永続的にどのように保存されているかという低レベルの詳細には関知しない。意味的手法は最も特定性の高い結果を出す傾向があるが、計算コストも最も高くなる傾向がある。

In current literature, researchers use a number of terms to refer to various approximate matching methods: fuzzy hashing and similarity hashing denote bytewise approximate matching; perceptual hashing and robust hashing denote semantic approximate matching. There is no widely-used pre-existing terminology for syntactic approximate matching as it is mostly viewed as pre-processing (to separate the features) before hashing, or applying a bytewise approximate matching algorithms. For example, network flows are usually reconstructed before any processing is done on them.

原本 PDF p.11

現在の文献では、研究者はさまざまな近似マッチング手法を表すために複数の用語を使っている。ファジーハッシュおよび類似性ハッシュはバイト単位の近似マッチングを指し、知覚ハッシュおよびロバストハッシュは意味的な近似マッチングを指す。構文的な近似マッチングについては、広く使われている既存の用語がない。これは、ハッシュ処理またはバイト単位の近似マッチングの前に特徴を分離する前処理とみなされることが多いためである。たとえば、ネットワークフローは通常、処理を始める前に再構成される。

Bytewise approximate matching algorithms work in two phases. In the first, a similarity digest representation (also referred to as a signature or fingerprint) is generated from the original data. In the second phase, digests are compared to produce a similarity score. More precisely:

原本 PDF p.11

バイト単位の近似マッチングアルゴリズムは2段階で動作する。第1段階では、元データから類似性ダイジェスト表現（シグネチャまたはフィンガープリントとも呼ばれる）を生成する。第2段階では、ダイジェストを比較して類似性スコアを算出する。より正確には、次のとおりである。

Similarity digest. A similarity digest is a (compressed) representation of the original data object’s feature set that is suitable for comparison with other similarity digests created by the same algorithm. In most cases, the digest is much smaller than the original artifact and the original object is not recoverable from the digest.

原本 PDF p.11

類似性ダイジェスト（Similarity digest）。類似性ダイジェストとは、同じアルゴリズムで作成された他の類似性ダイジェストと比較できるようにした、元のデータオブジェクトの特徴集合の（圧縮された）表現である。ほとんどの場合、ダイジェストは元の成果物より大幅に小さく、ダイジェストから元のオブジェクトを復元することはできない。

Every bytewise approximate matching technique requires at least two core functions:

原本 PDF p.11

バイト単位の近似マッチング手法には、少なくとも次の2つの中核機能が必要である。

Feature extraction function: identifies and extracts features/attributes from each digital artifact. The mechanism by which features are picked and interpreted depends on the approximate matching algorithm. The representation of this collection is the similarity digest of the object. Similarity function: compares two similarity digests and outputs a score. The recommended approach is to assign a score \(s\) in the \(0 \le s \le 1\) range, where 0 indicates no similarity and 1 indicates high similarity. This score represents a normalized estimate of the number of matching features in the feature sets corresponding to the artifacts from which the similarity digests were created. Normalization strategy: The similarity function can follow one of two normalization strategies, depending on whether the algorithm describes resemblance or containment. For resemblance queries, the number of matching features will be weighed against the total number of features in both objects. In the case of containment queries, the algorithm may disregard unmatched features in the larger of the objects’ two-feature sets.

原本 PDF p.11

特徴抽出関数：各デジタル成果物から特徴または属性を特定して抽出する。特徴の選択・解釈方法は近似マッチングアルゴリズムによって異なる。この特徴群の表現が、オブジェクトの類似性ダイジェストとなる。類似性関数：2つの類似性ダイジェストを比較し、スコアを出力する。推奨される方法は、スコア \(s\) を \(0 \le s \le 1\) の範囲で割り当てることであり、0は類似性なし、1は高い類似性を示す。このスコアは、類似性ダイジェストの生成元である成果物に対応する特徴集合のうち、一致する特徴数の正規化推定値である。正規化方法：類似性関数は、アルゴリズムが類似クエリと包含クエリのどちらを扱うかに応じて、次の2つの正規化方法のいずれかを使う。類似クエリでは、一致する特徴数を両方のオブジェクトの特徴総数と比較する。包含クエリでは、2つの特徴集合のうち大きい方に含まれる不一致特徴を無視してもよい。

Because features and feature sets can be arbitrarily complex and, furthermore, deal with byte-level structures to which meaning is not clearly assigned, the interpretation of the similarity score can prove challenging. To address this problem, some approximate matching algorithms make use of an empirically determined threshold value to attempt to correlate bytewise similarity scores with higher-level properties of interest. In such cases, the similarity score can be treated as a confidence score, where results above the threshold value are considered likely to exhibit common human-recognizable traits.

原本 PDF p.11

特徴や特徴集合は任意に複雑になり得るうえ、意味が明確に割り当てられていないバイトレベルの構造を扱うこともあるため、類似性スコアの解釈は難しい場合がある。この問題に対処するため、経験的に決定したしきい値を使い、バイト単位の類似性スコアを、より高レベルの関心対象の特性と対応付けようとする近似マッチングアルゴリズムもある。この場合、類似性スコアを信頼度スコアとして扱い、しきい値を上回る結果は、人が認識できる共通の特徴を示す可能性が高いとみなせる。

原本 PDF p.11

2.3 必須要件

Like traditional hash functions, there are several defining characteristics that approximate matching functions should exhibit. Each algorithm should define how it incorporates each of these properties and how it satisfies the reporting requirements for those properties, where appropriate.

従来のハッシュ関数と同様に、近似マッチング関数が示すべき、いくつかの定義上の特性がある。各アルゴリズムは、これらの特性のそれぞれをどのように取り入れるか、また該当する場合はそれらの特性に関する報告要件をどのように満たすかを定めるべきである。

Similarity preservation: Similarity digests must be constructed such that the outcome of a comparison between any two digests is uniquely determined by the similarity of the artifacts from which they were produced. That is, if \(A'\) is a similarity digest created from artifact \(A\) and \(B'\) is a similarity digest created from artifact \(B\), the results of comparing \(A'\) and \(B'\) should be uniquely determined by the similarity of \(A\) and \(\mathrm{B}\). Self-evaluation: The similarity measure should be accompanied by a measure of the accuracy of the matching technique under the circumstances in which it is used, e.g., a margin of error or confidence level. The description of the output score should also state whether a score of 1 indicates an exact match. Compression: A compact similarity digest is desired as it normally allows a faster comparison and requires less storage space. In the best case, it will have a fixed length like the output of traditional hash functions. If the efficiency and reliability of the results remains unchanged, then a shorter similarity digest is preferable. Ease of computation: First, the algorithm description should include the results of testing the runtime efficiency of the feature extraction function and of the similarity function. The former might be expressed relative to a standard hashing algorithm, such as SHA-1. Second, the algorithm description should state the theoretical complexity for a similarity digest comparison in big O notation. For instance, common lookup complexities for comparing a single digest against a database with \(n\) entries, are: \(O(1)\) for fixed-length digests stored in hash tables (e.g. dictionaries) \(O(\log_2 n)\) for fixed-length digests stored in binary trees or a sorted list

類似性の保持：類似性ダイジェストは、任意の2つのダイジェストを比較した結果が、それらの生成元である成果物の類似性によって一意に決まるように構成しなければならない。つまり、\(A'\) が成果物 \(A\) から作成した類似性ダイジェストであり、\(B'\) が成果物 \(B\) から作成した類似性ダイジェストである場合、\(A'\) と \(B'\) の比較結果は、\(A\) と \(\mathrm{B}\) の類似性によって一意に決まるべきである。自己評価：類似性尺度には、それが使用される状況における照合手法の精度を示す尺度（誤差範囲や信頼水準など）を併記すべきである。出力スコアの説明では、スコア1が完全一致を表すかどうかも明記すべきである。圧縮：コンパクトな類似性ダイジェストが望ましい。通常、比較を高速化でき、必要な記憶領域も少なくて済むためである。最良の場合、従来のハッシュ関数の出力のように固定長となる。結果の効率性と信頼性が変わらないなら、類似性ダイジェストは短い方が望ましい。計算の容易さ：第一に、アルゴリズムの説明には、特徴抽出関数および類似性関数の実行時効率を試験した結果を含めるべきである。前者は、SHA-1などの標準的なハッシュアルゴリズムとの相対値で表してもよい。第二に、アルゴリズムの説明では、類似性ダイジェストの比較に関する理論計算量をビッグO記法で示すべきである。たとえば、\(n\) 件のエントリを持つデータベースに対して単一のダイジェストを比較する場合の一般的な検索計算量は、次のとおりである。\(O(1)\)：ハッシュテーブル（辞書など）に格納した固定長ダイジェスト。\(O(\log_2 n)\)：二分木またはソート済みリストに格納した固定長ダイジェスト。

3.1 Motivation

3.1 動機

There are at least three major motivations for testing bytewise approximate matching algorithms. The first and most basic is to understand the classes of objects that the algorithm identifies as similar. Testing against a fixed set of tasks helps to highlight any changes in the algorithm’s similarity score as a function of its input. Improvements in speed or space efficiency can also be measured.

原本 PDF p.14

第二に、アルゴリズムの開発中、Breitinger、Stivaktakis、Baierが提案したもの[3]などの標準テスト一式を用いれば、新しいバージョンを以前のバージョンと比較できる。固定された一連のタスクでテストすると、入力に応じたアルゴリズムの類似性スコアの変化を明らかにできる。速度や記憶領域の効率向上も測定できる。

Finally, testing allows approximate matching algorithms to be compared to each other. The use of a standard suite of tasks can be beneficial in this testing scenario also. Additional measures must be taken, however, to ensure that tests produce comparable results. Because the algorithms define their similarity score independently, direct comparison of scores is rarely meaningful. One solution for this problem is to use a threshold or some other criteria to translate scores from their [0,1] range back to a binary {0,1} output which can be evaluated against known ground truth to produce confusion matrices (Roussev’s comparison of sdhash and ssdeep offers an example of this approach [2]). Alternately, the tester might define other high-level criteria for the expected behavior of an algorithm in a specific use case of interest, and evaluate the algorithms against this expectation.

原本 PDF p.14

最後に、テストによって近似マッチングアルゴリズム同士を比較できる。このテストシナリオでも、標準的なタスク一式の使用が有益となり得る。ただし、テストが比較可能な結果を生むようにするには、追加の対策を講じなければならない。各アルゴリズムは類似性スコアを独自に定義しているため、スコアを直接比較しても意味をなすことはほとんどない。この問題の解決策の一つは、しきい値またはその他の基準を使って、[0,1] の範囲のスコアを二値の {0,1} の出力に変換し直すことである。この出力は、既知の正解データと照らして評価し、混同行列を作成できる（Roussevによるsdhashとssdeepの比較は、この方法の例である[2]）。別の方法として、テスト実施者が、関心のある特定のユースケースにおいてアルゴリズムに期待される動作について別の高レベルの基準を定め、その期待に照らして各アルゴリズムを評価してもよい。

3.2 Test Data

原本 PDF p.14

3.2 テストデータ

Approximate matching algorithms can be tested against either controlled (synthetic) data [7] or real data (i.e., data originally created for purposes other than testing). The former typically consists of randomly generated blocks or files; its main advantage is that ground truth is constructed and, therefore, precisely known. This allows tests to be run automatically and the results to be interpreted with standard statistical measures.

原本 PDF p.14

近似マッチングアルゴリズムは、制御された（合成）データ[7]または実データ（つまり、もともとテスト以外の目的で作成されたデータ）のいずれかを使ってテストできる。前者は通常、ランダムに生成したブロックまたはファイルで構成される。その主な利点は、正解データが構築されたものであり、したがって正確に分かっていることである。このため、テストを自動実行し、標準的な統計指標を使って結果を解釈できる。

The drawback to using randomly generated data is that it is not necessarily representative. For example, random data tends to be unique, high-entropy and internally varied. These properties may be appropriate for use cases involving compressed or encrypted data, but could prove misleading for other file types (such as text documents). A potential workaround is to develop more sophisticated randomization that preserves the characteristic properties of the target file type.

原本 PDF p.14

ランダム生成データを使う欠点は、必ずしも代表性がないことである。たとえば、ランダムデータは一意性が高く、エントロピーが高く、内部の変化に富む傾向がある。これらの特性は、圧縮データや暗号化データを扱うユースケースには適している可能性があるが、テキスト文書など、他の種類のファイルでは誤解を招くおそれがある。対象ファイル形式の特徴的な性質を保つ、より洗練されたランダム化を開発することが解決策となり得る。

The obvious advantage of using real data is that the results can be directly be related to practical applications. However, the challenges of defining a representative sample, establishing the ground truth, and running experiments at scale (without a human in the loop) are non-trivial. See Appendix A1 Example test methodologies for both controlled and real data.

原本 PDF p.15

実データを使用する明らかな利点は、結果を実際の応用に直接関連付けられることである。ただし、代表的なサンプルの定義、グラウンドトゥルースの確立、人を介さずに大規模な実験を実行することには、容易には解決できない課題がある。管理されたデータと実データの両方に関するテスト方法の例は、付録A1を参照されたい。

3.3 Properties of Special Interest

原本 PDF p.15

3.3 特に注目する性質

The following properties may be especially useful for testing and comparing approximate matching algorithms. This list is not meant to be exhaustive. Note that the properties enumerated here are adapted from those proposed by Breitinger, Stivaktakis, and Baier [3]. See their work on the FRASH testing framework for an example of a complete description (including full implementation details and suggested test values) of a testing framework that incorporates these properties.

原本 PDF p.15

次の性質は、近似照合アルゴリズムのテストと比較に特に有用な場合がある。この一覧は網羅的なものではない。ここに挙げる性質は、Breitinger、Stivaktakis、Baierが提案したもの[3]をもとにしている。これらの性質を取り入れたテストフレームワークの完全な記述の例として、FRASHテストフレームワークに関する同著者らの研究を参照されたい。そこには、実装の詳細と推奨テスト値も含まれる。

3.3.1 Efficiency

原本 PDF p.15

3.3.1 効率

The efficiency of an algorithm is measured in terms of the space and time it requires; the latter property is further subdivided according to time needed for generating similarity digests and time need for comparing them.

原本 PDF p.15

アルゴリズムの効率は、必要とする空間と時間によって測定する。後者はさらに、類似性ダイジェストの生成に必要な時間と、その比較に必要な時間に分けられる。

Space efficiency.

原本 PDF p.15

空間効率。

Traditional hash functions return a fixed length fingerprint; in contrast, the length of similarity digests is sometimes variable and proportional to the input length. If the digest is of variable length, space efficiency measures the ratio between input and the digest and returns a percentage value. That is,

原本 PDF p.15

従来のハッシュ関数は固定長のフィンガープリントを返す。一方、類似性ダイジェストの長さは可変で、入力長に比例する場合がある。ダイジェストが可変長の場合、空間効率では両者の長さの比を測定し、百分率の値を返す。すなわち、次のとおりである。

\[\text{space efficiency}=\frac{\text{digest length}}{\text{input length}}\tag{1}\]
原本 PDF p.15
\[\text{空間効率}=\frac{\text{ダイジェスト長}}{\text{入力長}}\tag{1}\]

Generation efficiency.

原本 PDF p.15

生成効率。

Generation efficiency measures the throughput of an algorithm when producing a similarity digest from raw input. To enable useful comparisons across different architectures, it is recommended that the throughput of a standard algorithm implementation, such as SHA-1 in openssh, be included as a reference point.

原本 PDF p.15

生成効率は、生の入力から類似性ダイジェストを生成する際のアルゴリズムのスループットを測定する。異なるアーキテクチャ間で有用な比較ができるよう、opensshにおけるSHA-1など、標準的なアルゴリズム実装のスループットを基準点として含めることが推奨される。

Comparison efficiency.

原本 PDF p.15

比較効率。

The comparison efficiency measures the rate at which similarity digests can be compared. It is useful to have both a formal analysis, which provides the theoretical complexity of the comparison (in O- notation) and an empirical evaluation based on a reference data set.

原本 PDF p.15

比較効率は、類似性ダイジェストを比較できる速度を測定する。比較の理論的計算量をO記法で示す形式的な分析と、基準データセットに基づく実測評価の両方を行うことが有用である。

A related property of note is the ability of the algorithm to leverage parallel computational resources; these may include conventional multi-core CPU architectures, as well as massively parallel ones, such as GPUs. To that end, tests should include scalability analysis, which shows speedup as a function of available hardware concurrency.

原本 PDF p.15

関連する性質として、並列計算資源を活用できることも挙げられる。これには、従来のマルチコアCPUアーキテクチャや、GPUなどの大規模な並列アーキテクチャが含まれる。このため、テストには、利用可能なハードウェアの並列性に応じてどの程度高速化するかを示すスケーラビリティ分析を含めるべきである。

3.3.2 Sensitivity

原本 PDF p.15

3.3.2 感度

Sensitivity is a measure of the ability of an approximate matching algorithm to find correlations among objects based on fine-grained commonality—the smaller the features being correlated, the more sensitive the algorithm is. Clearly, there is a threshold below which the sensitivity will be too high and all objects will appear similar; it is up to the algorithm designer to identify that threshold and incorporate it into the implementation.

Two examples of tests for measuring an algorithm’s sensitivity are fragment detection and single-common-block correlation.

原本 PDF p.15

感度は、細かな共通性に基づいてオブジェクト間の相関を見つける、近似照合アルゴリズムの能力の尺度である。相関の対象となる特徴が小さいほど、アルゴリズムの感度は高い。ただし、対象とする特徴があるしきい値より小さくなると感度が高すぎて、すべてのオブジェクトが類似しているように見える。アルゴリズムの設計者がそのしきい値を特定し、実装に組み込む必要がある。

アルゴリズムの感度を測定するテストの例として、断片検出と単一共通ブロックの相関の2つがある。

•Fragment detection. Fragment detection quantifies the length of the shortest sample from a data object, for which the similarity tool reliably correlates the sample and the whole object. Common uses include correlating a disk block, or network packet to file.

原本 PDF p.16

•断片検出。断片検出では、類似性ツールがサンプルとオブジェクト全体を確実に相関付けられる、データオブジェクトからの最短サンプルの長さを定量化する。一般的な用途には、ディスクブロックまたはネットワークパケットをファイルに相関付けることが含まれる。

•Single-common-block correlation. The single-common-block correlation test is designed to characterize the behavior of an algorithm in the case where two files share a single common object. That is, given two files f₁ and f₂ that share a common object O (but are otherwise dissimilar), what is the smallest O for which the similarity tool reliably correlates the two targets?

原本 PDF p.16

•単一共通ブロック相関。このテストは、2つのファイルが1つの共通オブジェクトを共有している場合のアルゴリズムの動作を特徴付ける。つまり、オブジェクト O を1つ共有する（それ以外は互いに異なる）2つのファイル f₁ と f₂ があるとき、類似性ツールが2つの対象を確実に相関付けるために必要な O の最小サイズはどれくらいか、という問いである。

3.3.3 Robustness

原本 PDF p.16

3.3.3 堅牢性

Robustness is a measure of the ability of an approximate matching algorithm to find correlation among related objects in the presence of noise and routine transformations. Common transformations include internal fragmentation (e.g., during network transmission) and misalignment (adding content during artifact editing).

原本 PDF p.16

堅牢性とは、ノイズや日常的な変換が加わった状態でも、近似マッチングアルゴリズムが関連オブジェクト間の相関を見つけられる能力を測る指標である。一般的な変換には、内部断片化（例：ネットワーク伝送時）や位置ずれ（成果物の編集時に内容が追加されること）が含まれる。

Alignment robustness and white noise resistance are examples of tests that measure an algorithm’s robustness.

原本 PDF p.16

位置合わせに対する堅牢性とホワイトノイズ耐性は、アルゴリズムの堅牢性を測定するテストの例である。

•Alignment robustness. Alignment robustness is an attempt to quantify the sensitivity of an algorithm to alignment shifts. Specifically, the test analyzes the impact of inserting sequences of bytes at the beginning of one of the compared artifacts.

原本 PDF p.16

•位置合わせに対する堅牢性。位置合わせに対する堅牢性は、アルゴリズムが位置ずれにどの程度敏感かを定量化する試みである。具体的には、比較対象の成果物の一方の先頭にバイト列を挿入した場合の影響を分析する。

•White noise resistance. This test measures the amount of (uniformly) random noise that can be added to an object before the approximate matching algorithm becomes unable to correlate the original and the modified version. For example, for ssdeep [5] it was shown that a few changes distributed over the input are sufficient to prevent a match [6].

原本 PDF p.16

•ホワイトノイズ耐性。このテストでは、近似マッチングアルゴリズムが元のオブジェクトと変更後のオブジェクトを相関付けられなくなるまでに、オブジェクトへ追加できる（一様な）ランダムノイズの量を測定する。たとえばssdeep [5]では、入力全体に分散したわずかな変更だけでマッチを妨げるのに十分であることが示されている[6]。

Appendix 2: Approximate longest common substring

原本 PDF p.20

付録2：近似最長共通部分文字列

The basic idea of the approximate longest common substring metric (aLCS) is not to compare files byte-by-byte but rather block-by-block. To identify the blocks, we apply the rolling hash from ssdeep. Our settings aim at having blocks of ≈ 80 bytes. Instead of comparing blocks bytewise, each one is hashed and compared using the 64-bit FNV-1a hash [8]. Besides the hash value, we also store the entropy and length for each block in a final linear list called alcs-digest; a reference implementation is publicly available.1

原本 PDF p.20

近似最長共通部分文字列（aLCS）指標の基本的な考え方は、ファイルをバイトごとに比較するのではなく、ブロックごとに比較することである。ブロックの特定にはssdeepのローリングハッシュを適用する。設定では、ブロックの大きさを約80バイトとする。ブロックをバイト単位で比較する代わりに、それぞれをハッシュ化し、64ビットFNV-1aハッシュ[8]で比較する。ハッシュ値に加えて各ブロックのエントロピーと長さを保存し、alcs-digestと呼ぶ最終的な線形リストを作成する。参照実装は公開されている。1

Let La denote the absolute longest common substring of two alcs-digests. Comparing two alcs-digests is equal to comparing two linear lists. If the hash of an item on list A has the same value as the hash of an item on list B, we are convinced that La is greater than or equal to the length of the blocks corresponding to the hashes. If two consecutive items on list A have the same hash values as two consecutive items on list B, we sum up the length of both blocks to receive La. Of course, the usage of hash functions implies the possibility of false positives. Nevertheless, this is an easy and fast method to get a good estimation of the longest common substring.

原本 PDF p.20

Laを2つのalcs-digest間の絶対最長共通部分文字列とする。2つのalcs-digestの比較は、2つの線形リストの比較に等しい。リストA上の項目のハッシュ値がリストB上の項目のハッシュ値と一致すれば、該当するブロックの長さ以上のLaがあると判断できる。リストA上の連続する2項目のハッシュ値がリストB上の連続する2項目と一致する場合、両ブロックの長さを合計してLaを得る。もちろん、ハッシュ関数の使用には偽陽性の可能性が伴う。それでも、最長共通部分文字列を適切に推定するための簡便で高速な方法である。
