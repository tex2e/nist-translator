3 Introduction

原本 PDF p.6

3 はじめに

未レビュー訳

This Recommendation specifies a message authentication code (MAC) algorithm that is based on a symmetric key block cipher. This cipher-based MAC is abbreviated CMAC, analogous to the abbreviation for the hash function-based MAC, HMAC, that is standardized in FIPS Pub. 198 [4]. CMAC may be appropriate for information systems in which an approved block cipher is more readily available than an approved hash function.

原本 PDF p.6

本推奨事項は、対称鍵ブロック暗号に基づくメッセージ認証コード（MAC）アルゴリズムを規定します。この暗号ベースのMACはCMACと略され、FIPS Pub. 198 [4]で標準化されたハッシュ関数ベースのMACの略称HMACに対応しています。承認済みのハッシュ関数よりも承認済みのブロック暗号を容易に利用できる情報システムでは、CMACが適切な場合があります (may)。

未レビュー訳

The basic Cipher Block Chaining MAC algorithm (CBC-MAC) has security deficiencies [9]. The core of the CMAC algorithm is a variation of CBC-MAC that Black and Rogaway proposed and analyzed under the name XCBC in Ref. [2] and submitted to NIST in Ref. [1]. The XCBC algorithm efficiently addresses the security deficiencies of CBC-MAC. Iwata and Kurosawa proposed an improvement of XCBC and named the resulting algorithm One-Key CBC-MAC (OMAC) in Ref. [6] and in Ref. [5], their initial submission to NIST; they later submitted OMAC1 [7], a refinement of OMAC, and additional security analysis [8]. The OMAC1 variation efficiently reduces the key size of XCBC. CMAC is equivalent to OMAC1.

原本 PDF p.6

基本的なCipher Block Chaining MACアルゴリズム（CBC-MAC）にはセキュリティ上の欠陥があります [9]。CMACアルゴリズムの中核はCBC-MACの変形であり、BlackとRogawayが文献[2]で提案・分析し、文献[1]でNISTに提出したもので、XCBCという名称です。XCBCアルゴリズムはCBC-MACのセキュリティ上の欠陥に効率的に対処します。IwataとKurosawaはXCBCを改良し、文献[6]およびNISTへの最初の提出文献[5]において、そのアルゴリズムをOne-Key CBC-MAC（OMAC）と命名しました。その後、OMACの改良版であるOMAC1 [7]と、追加のセキュリティ分析[8]を提出しました。OMAC1の変形はXCBCの鍵サイズを効率的に縮小します。CMACはOMAC1と等価です。

未レビュー訳

Because CMAC is based on an approved symmetric key block cipher, such as the Advanced Encryption Standard (AES) algorithm that is specified in Federal Information Processing Standard (FIPS) Pub. 197 [3], CMAC can be considered a mode of operation of the block cipher. CMAC is also an approved mode of the Triple Data Encryption Algorithm (TDEA) [10]; however, as discussed in Appendix B, the recommended default message span for TDEA is much more restrictive than for the AES algorithm, due to the smaller block size of TDEA.

原本 PDF p.6

CMACは、連邦情報処理標準（FIPS）Pub. 197 [3]で規定されるAdvanced Encryption Standard（AES）アルゴリズムなどの承認済み対称鍵ブロック暗号に基づくため、ブロック暗号の運用モードとみなすことができます (can)。CMACはTriple Data Encryption Algorithm（TDEA）[10]の承認済み運用モードでもあります。ただし、付録Bで説明するように、TDEAのブロックサイズはAESアルゴリズムより小さいため、TDEAに推奨される既定のメッセージ範囲はAESの場合よりもはるかに制限されています。

未レビュー訳

CMAC, like any well-designed MAC algorithm, provides stronger assurance of data integrity than a checksum or an error detecting code. The verification of a checksum or an error detecting code is designed to detect only accidental modifications of the data, while CMAC is designed to detect intentional, unauthorized modifications of the data, as well as accidental modifications.

原本 PDF p.6

適切に設計された他のMACアルゴリズムと同様に、CMACはチェックサムまたは誤り検出符号よりも強いデータ完全性の保証を提供します。チェックサムまたは誤り検出符号の検証は、データへの偶発的な変更のみを検出するよう設計されています。一方、CMACは、偶発的な変更に加え、意図的かつ許可されていないデータ変更を検出するよう設計されています。

5.2 Block Cipher

原本 PDF p.10

5.2 ブロック暗号

未レビュー訳

The CMAC algorithm depends on the choice of an underlying symmetric key block cipher. The CMAC algorithm is thus a mode of operation (a mode, for short) of the block cipher. The CMAC key is the block cipher key (the key, for short).

原本 PDF p.10

CMACアルゴリズムは、基礎となる対称鍵ブロック暗号の選択に依存します。したがって、CMACアルゴリズムはブロック暗号の運用モード（略して「モード」）です。CMAC鍵はブロック暗号鍵（略して「鍵」）です。

未レビュー訳

For any given key, the underlying block cipher of the mode consists of two functions that are inverses of each other. The choice of the block cipher includes the designation of one of the two functions of the block cipher as the forward function/transformation, and the other as the inverse function, as in the specifications of the AES algorithm and TDEA in Ref. [3] and Ref. [10], respectively. The CMAC mode does not employ the inverse function.

原本 PDF p.10

任意の所与の鍵について、このモードの基礎となるブロック暗号は、互いに逆関数である2つの関数から成ります。ブロック暗号の選択には、AESアルゴリズムおよびTDEAの仕様（それぞれ文献[3]および[10]）と同様に、ブロック暗号の2つの関数の一方を順方向関数／変換として、もう一方を逆関数として指定することが含まれます。CMACモードは逆関数を使用しません。

未レビュー訳

The forward cipher function is a permutation on bit strings of a fixed length; the strings are called blocks. The bit length of a block is denoted b, and the length of a block is called the block size. For the AES algorithm, b = 128; for TDEA, b = 64. The key is denoted K, and the resulting forward cipher function of the block cipher is denoted CIPHK.

原本 PDF p.10

順方向暗号関数は、固定長のビット列に対する置換です。このビット列をブロックと呼びます。ブロックのビット長を b と表記し、ブロックの長さをブロックサイズと呼びます。AESアルゴリズムでは b = 128、TDEAでは b = 64 です。鍵は K と表記し、ブロック暗号の順方向暗号関数を CIPHK と表記します。

未レビュー訳

The key shall be secret and shall be used exclusively for the CMAC mode of the chosen block cipher. The message span of the key is discussed in Appendix B. To fulfill the requirements on the key, the key should be established among the parties to the information within an approved key management structure; the details of the establishment and management of keys are outside the scope of this Recommendation.

5.3 Subkeys

原本 PDF p.11

5.3 サブキー

未レビュー訳

The block cipher key is used to derive two additional secret values, called the subkeys, denoted K1 and K2. The length of each subkey is the block size. The subkeys are fixed for any invocation of CMAC with the given key. Consequently, the subkeys may be precomputed and stored with the key for repeated use; alternatively, the subkeys may be computed anew for each invocation.

原本 PDF p.11

ブロック暗号鍵を用いて、サブキーと呼ばれる2つの追加の秘密値 K1 および K2 を導出します。各サブキーの長さはブロックサイズです。所与の鍵を用いるCMACの各実行では、サブキーは固定です。そのため、サブキーは事前計算して鍵とともに保存し、繰り返し使用できます (may)。または、実行ごとに新たに計算できます (may)。

未レビュー訳

Any intermediate value in the computation of the subkey, in particular, CIPHK(0b), shall also be secret. This requirement precludes the system in which CMAC is implemented from using this intermediate value publicly for some other purpose, for example, as an unpredictable value or as an integrity check value on the key.

原本 PDF p.11

サブキー計算における中間値、特に CIPHK(0b) も秘密にしなければなりません (shall)。この要件により、CMACの実装システムは、この中間値を予測不能値や鍵の完全性検査値など、他の目的で公開利用できません。

未レビュー訳

One of the elements of the subkey generation process is a bit string, denoted Rb, that is completely determined by the number of bits in a block. In particular, for the two block sizes of the currently approved block ciphers, R128 = 012010000111, and R64 = 05911011.

原本 PDF p.11

サブキー生成プロセスの要素の1つは、ビット列 Rb であり、これはブロック内のビット数によって完全に定まります。特に、現在承認されているブロック暗号の2つのブロックサイズについて、R128 = 012010000111、R64 = 05911011 です。

未レビュー訳

In general, Rb is a representation of a certain irreducible binary polynomial of degree b, namely, the lexicographically first among all such polynomials with the minimum possible number of nonzero terms. If this polynomial is expressed as ub + cb−1ub−1 + … + c2u2 + c1u + c0, where the coefficients cb−1, cb−2, …, c2, c1, c0 are either 0 or 1, then Rb is the bit string cb−1cb−2…c2c1c0.

原本 PDF p.11

一般に、Rb は次数 b の既約2進多項式の表現です。すなわち、可能な非零項の数が最小である多項式のうち、辞書順で最初のものです。この多項式を ub + cb−1ub−1 + … + c2u2 + c1u + c0 と表し、係数 cb−1、cb−2、…、c2、c1、c0 がいずれも0または1であるとすると、Rb はビット列 cb−1cb−2…c2c1c0 です。

未レビュー訳

The message span of a key is the total number of messages for which MACs are generated across all implementations of CMAC with that key. The message span of the key affects the security of the system against attacks that are based on the detection of a pair of distinct messages with the same MAC before its truncation3. Such a pair is called a collision4 in this appendix. As with other block cipher-based MAC algorithms, an attacker may be able to exploit a collision to produce the valid MAC for a new message, the content of which may be largely of the attacker’s choosing. Such an event would be a fundamental breach of the expected authentication assurance.

原本 PDF p.18

鍵のメッセージ範囲とは、その鍵を用いるCMACのすべての実装にわたってMACが生成されるメッセージの総数です。鍵のメッセージ範囲は、切詰め前に同一のMACを持つ相異なるメッセージの組を検出することに基づく攻撃に対するシステムの安全性に影響します3。この付録では、そのような組を衝突4と呼びます。他のブロック暗号ベースのMACアルゴリズムと同様に、攻撃者は衝突を悪用し、内容を大部分自ら選べる新しいメッセージに対する有効なMACを生成できる場合があります (may)。これは、期待される認証保証を根本から損なう事象です。

未レビュー訳

In principle, collisions must exist because there are many more possible messages than MACs; in practice, however, collisions may not occur among the messages for which MACs are actually generated during the lifetime of the key. The probability that at least one collision will occur depends mostly on the message span of the key relative to the block size, b, of the underlying block cipher. For example, a collision is expected to exist among a set of 2b/2 arbitrary messages; in other words, 264 messages for the AES algorithm, and 232 messages for TDEA. This property was one of the motivations to develop the AES with a block size of 128 bits.

原本 PDF p.18

原理上、MACよりも可能なメッセージの数がはるかに多いため、衝突は存在します (must)。しかし実際には、鍵の有効期間中にMACが生成されるメッセージ間で衝突が発生しない場合もあります (may not)。少なくとも1つの衝突が生じる確率は、基礎となるブロック暗号のブロックサイズ b に対する鍵のメッセージ範囲に主に依存します。例えば、任意のメッセージを2b/2 個集めると衝突が存在すると予想されます。すなわち、AESでは264 個、TDEAでは232 個のメッセージです。この性質が、AESのブロックサイズを128ビットとして開発した理由の1つでした。

未レビュー訳

A simple and prudent method to achieve this goal is to establish and enforce an appropriate limit on the message span of any CMAC key, which in turn limits the probability that a collision will even occur. For general-purpose applications, the default recommendation is to limit the key to no more than 248 messages when the block size of the underlying block cipher is 128 bits, as with the AES algorithm, and 221 messages when the block size is 64 bits, as with TDEA. Within these limits, the probability that a collision will occur is expected to be less than one in a billion for the AES algorithm, and less than one in a million for TDEA.

原本 PDF p.18

Appendix C: Protection Against Replay of Messages

原本 PDF p.19

付録C：メッセージの再送に対する保護

未レビュー訳

As described in Appendix A, the successful verification of a MAC for a message gives assurance that the source of the message executed the MAC generation algorithm to create the MAC; however, the party that presented the message and MAC for verification may not be the original source of the message. Therefore, the CMAC algorithm does not inherently prevent an attacker from intercepting a legitimate message and its MAC and “replaying” them for verification at a later time, for example, in an attempt to impersonate a party that has access to the key. In some protocols an attacker may even be able to present to a verifier a message-MAC pair that the verifier itself generated earlier in the protocol.

原本 PDF p.19

付録Aで説明したように、メッセージのMAC検証が成功すると、そのメッセージの送信元がMAC生成アルゴリズムを実行してMACを作成したことが保証されます。ただし、そのメッセージとMACを検証のために提示した者が、メッセージの元の送信元とは限りません (may not)。したがって、CMACアルゴリズム自体は、正当なメッセージとそのMACを攻撃者が傍受し、後刻の検証時に「再送」することを本質的には防止しません。例えば、鍵にアクセスできる者になりすますためです。一部のプロトコルでは、攻撃者が、検証者自身がプロトコルの前の段階で生成したメッセージとMACの組を検証者に提示できる場合さえあります (may)。

未レビュー訳

The controlling protocol or application may protect against such an event by incorporating certain identifying information into the initial bits of every message. Examples of such information include a sequential message number, a timestamp, or a nonce. Upon successful verification of the message, this information may provide a means for the detection of replayed messages, out-of-sequence messages, or missing messages.

原本 PDF p.19

制御するプロトコルまたはアプリケーションは、すべてのメッセージの先頭ビットに特定の識別情報を含めることで、このような事象から保護できます (may)。そのような情報の例には、連続するメッセージ番号、タイムスタンプ、またはノンスがあります。メッセージの検証に成功したとき、この情報によって、再送メッセージ、順序が前後したメッセージ、または欠落したメッセージを検出できる場合があります (may)。
