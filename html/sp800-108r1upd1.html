Introduction

原本 PDF p.9

はじめに

未レビュー訳

When a party obtains a cryptographic key, additional keys will often be needed. There are numerous methods for obtaining the keying material required by approved cryptographic algorithms (see SP 800-133, Rev. 2 [1] for a discussion of the recommended techniques). The requisite keying material is often obtained from the output of a key-derivation function (KDF) that takes a preexisting cryptographic key (and other data) as input. Key-derivation functions are used to derive additional keys from a cryptographic key. The key-derivation functions specified in the original edition (2008) of NIST Special Publication (SP) 800-1081 used HMAC and CMAC as pseudorandom functions. In Revision 1, a KDF using KMAC is added in Section 4.4.

原本 PDF p.9

暗号鍵を取得した後、追加の鍵が必要になることが多い。承認済み暗号アルゴリズムに必要な鍵素材を得る方法は多数ある（推奨技法についてはSP 800-133 Rev. 2 [1]を参照）。必要な鍵素材は、多くの場合、既存の暗号鍵（およびその他のデータ）を入力とする鍵導出関数（KDF）の出力から得られる。KDFは暗号鍵から追加の鍵を導出するために使用される。NIST特別刊行物（SP）800-108の初版（2008年）[1]で規定したKDFは、HMACとCMACを疑似乱数関数として用いていた。改訂1では、第4.4節にKMACを用いるKDFを追加した。

Scope and Purpose

原本 PDF p.10

適用範囲と目的

未レビュー訳

This Recommendation specifies several families of key-derivation functions that use pseudorandom functions. These key-derivation functions can be used to derive additional keys from an existing cryptographic key that was previously established through an automated key-establishment scheme (e.g., as defined in SP 800-56A [2] and SP 800-56B [3]), previously generated (e.g., using a pseudorandom bit generator as specified in SP 800-90A [4] or a previous instance of key derivation as specified in this Recommendation), and/or previously shared in some other way (e.g., by manual distribution). Effectively, the key-derivation functions specified in this Recommendation provide the key expansion functionality described in SP 800-56C [5], where key derivation is portrayed as a process that potentially requires two separate steps: 1) randomness extraction (to obtain an initial key) and 2) key expansion (to produce additional keys from that initial key and other data).

原本 PDF p.10

本勧告は、疑似乱数関数を用いる複数の鍵導出関数群を規定する。これらの鍵導出関数は、自動鍵確立方式（例：[2]のSP 800-56Aおよび[3]のSP 800-56Bに規定）によって以前に確立された暗号鍵、既に生成された暗号鍵（例：[4]のSP 800-90Aに規定する疑似乱数ビット生成器を用いて生成したもの、または本勧告に規定する鍵導出を以前に実行して得たもの）、および／またはその他の方法（例：手動配布）で以前に共有された暗号鍵から、追加の鍵を導出するために使用できる。実質的に、本勧告に規定する鍵導出関数は、SP 800-56C [5]で説明される鍵拡張機能を提供する。同文書では、鍵導出は、場合によっては二つの別個の段階、すなわち1) 初期鍵を得るためのランダム性抽出、2) その初期鍵およびその他のデータから追加の鍵を生成する鍵拡張、を必要とする処理として示されている。

The Length of a Key-Derivation Key

原本 PDF p.22

6.2 鍵導出鍵の長さ

未レビュー訳

It is recommended that the length of a KDK used by a KDF be at least as large as the targeted security strength (in bits) of any application that will be supported by the use of the derived keying material. This may affect the choice of the MAC algorithm used to implement a PRF-based key-derivation function, since the possibilities for the KDK size are determined by what is allowed for the MAC keys. For example, when using CMAC as a PRF, the key length is uniquely determined by the underlying block cipher. In this case, an implementation should check whether the key-derivation key length is consistent with the length required by the PRF. However, some PRFs can accommodate different key lengths. If HMAC is used as the PRF, then a KDF can use a key-derivation key of essentially any length. It is worth noting, however, that if the chosen key is longer than one input block for the hash function underlying HMAC, that key will be hashed, and the (much shorter) h-bit output will be used as the HMAC key instead. In this case, given a pair consisting of the input data (other than the key) and enough corresponding output of the KDF, the hashed key can likely be recovered in (at most) 2h computations of the KDF. Therefore, the security strength of an HMAC-based key-derivation function may be decreased by increasing the length of the KDK beyond the length of an input block of the underlying hash function.

原本 PDF p.22

KDFで用いるKDKの長さは、導出鍵素材を利用するアプリケーションが目標とするセキュリティ強度（ビット単位）以上であることが推奨される。これは、PRFベースの鍵導出関数を実装するMACアルゴリズムの選択に影響することがある。KDKのサイズはMAC鍵に許容されるサイズによって決まるためである。例えば、CMACをPRFとして使用する場合、鍵長は基礎となるブロック暗号によって一意に決まる。この場合、実装ではKDKの長さがPRFに必要な長さと整合しているか確認すべきである。ただし、一部のPRFは異なる鍵長に対応できる。HMACをPRFとして用いる場合、KDFでは実質的に任意の長さのKDKを使用できる。ただし、選択した鍵がHMACの基礎となるハッシュ関数の1入力ブロックより長い場合、その鍵はハッシュされ、その代わりに（はるかに短い）hビットの出力がHMAC鍵として使用される。この場合、入力データ（鍵以外）と十分な対応するKDF出力の組があれば、ハッシュされた鍵を最大2^h回のKDF計算で復元できる可能性が高い。したがって、HMACベースの鍵導出関数では、KDKを基礎ハッシュ関数の入力ブロック長より長くすることでセキュリティ強度が低下することがある。

Converting Keying Material to Cryptographic Keys

原本 PDF p.23

6.3 導出鍵素材から暗号鍵への変換

未レビュー訳

The length of the derived keying material L depends on the requirements of the cryptographic algorithms that rely on the KDF output. The length of a given cryptographic key is determined by the algorithm that will employ it (e.g., a block cipher or a message authentication code) and the desired security strength. In the absence of limitations that may be imposed by relying applications, any segment of the derived keying material that has the required length can be specified for use as a key, subject to the following restriction: when multiple keys (or any other types of parameters, such as initialization vectors) are obtained from the derived keying material, they shall be selected from disjointed (i.e., non-overlapping) segments of the KDF output. Therefore, the value of L shall be greater than or equal to the sum of the lengths of the keys and other types of parameters that will be obtained from the derived keying material. Care must be taken to avoid confusion when parsing KDF output if any segments are used as public parameters (such as public IVs). Attacks on the protocol level may attempt to cause one party to mistakenly release a secret portion of the KDF output. The security of any protocol using the derived keying material is beyond the scope of this Recommendation. The use of the derived keying material as a key stream (as in a stream cipher) is not recommended because the security of using KDFs as stream cipher algorithms has not been sufficiently investigated.

原本 PDF p.23

導出鍵素材の長さLは、KDF出力を利用する暗号アルゴリズムの要件によって決まる。暗号鍵の長さは、その鍵を使用するアルゴリズム（例：ブロック暗号またはメッセージ認証コード）と、求めるセキュリティ強度によって決まる。利用側アプリケーションが課す制限がない場合、必要な長さを持つ導出鍵素材の任意の区間を鍵として指定できる。ただし、導出鍵素材から複数の鍵（または初期化ベクトルなど他種のパラメータ）を得る場合、それらはKDF出力の互いに重ならない区間から選ばなければならない。したがって、Lは、導出鍵素材から得る鍵およびその他のパラメータの長さの合計以上でなければならない。区間を公開パラメータ（公開IVなど）として使用する場合、KDF出力を解析するときに混乱が生じないよう注意が必要である。プロトコル層の攻撃により、一方の当事者がKDF出力の秘密部分を誤って開示するよう仕向けられる可能性がある。導出鍵素材を用いるプロトコルのセキュリティは、本勧告の対象外である。導出鍵素材を鍵ストリーム（ストリーム暗号など）として使用することは推奨されない。KDFをストリーム暗号アルゴリズムとして用いる安全性が十分に調査されていないためである。

6.4 入力データの符号化

未レビュー訳

Context Binding

原本 PDF p.24

6.6 コンテキストの結び付け

未レビュー訳

Derived keying material should be bound to all relying entities and other information to identify the derived keying material. This is called context binding. In particular, the identity (or identifier, as the term is defined in [2] and [3]) of each entity that will access (i.e., derive, hold, use, and/or distribute) any segment of the keying material should be included in the Context string input to the KDF, provided that this information is known by each entity who derives the keying material. In addition to identities, other information related to the derived keying material (e.g., session identifiers, sequence numbers) as well as a nonce may be included in the Context string, assuming that the information can be communicated (e.g., by means of the relying protocol). Context binding may not necessarily increase the security strength of an application that makes use of a derived key. However, the binding may provide a way to detect protocol errors by providing assurance that all parties who (correctly) derive the keying material share the same understanding of who will access it and in which session it will be used. If those parties have different understandings, then they will derive different keying material. When that keying material is used in a protocol, the protocol will likely fail to complete its execution and, therefore, will indicate errors to the participants.
