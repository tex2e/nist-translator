Abstract

原本 PDF p.5

概要

This Recommendation defines a mode of operation, called CCM, for a symmetric key block cipher algorithm. CCM may be used to provide assurance of the confidentiality and the authenticity of computer data by combining the techniques of the Counter (CTR) mode and the Cipher Block Chaining-Message Authentication Code (CBC-MAC) algorithm.

原本 PDF p.5

本勧告は、共通鍵ブロック暗号アルゴリズムの動作モードとしてCCMと呼ばれる方式を定義する。CCMは、カウンター（CTR）モードと暗号ブロック連鎖メッセージ認証コード（CBC-MAC）アルゴリズムの技法を組み合わせることで、コンピューター・データの機密性と真正性を保証するために使用できる。

KEY WORDS: authenticated encryption; authentication; block cipher; confidentiality; cryptography; encryption; information security; message authentication code; mode of operation.

3 Introduction

原本 PDF p.7

3 はじめに

This Recommendation specifies an algorithm, Counter with Cipher Block Chaining-Message Authentication Code [1], abbreviated CCM, that can provide assurance of the confidentiality and authenticity of data. CCM is based on an approved symmetric key block cipher algorithm whose block size is 128 bits, such as the Advanced Encryption Standard (AES) algorithm currently specified in Federal Information Processing Standard (FIPS) Pub. 197 [2]; thus, CCM cannot be used with the Triple Data Encryption Algorithm [3], whose block size is 64 bits. CCM can be considered a mode of operation of the block cipher algorithm. As with other modes of operation, a single key to the block cipher must be established beforehand among the parties to the data; thus, CCM should be implemented within a well-designed key management structure. The security properties of CCM depend, at a minimum, on the secrecy of the key.

原本 PDF p.7

本勧告は、データの機密性と真正性を保証できるアルゴリズムであるCounter with Cipher Block Chaining-Message Authentication Code [1]（略称CCM）を規定する。CCMは、ブロック長が128ビットの承認済み共通鍵ブロック暗号アルゴリズムに基づく。例えば、現在Federal Information Processing Standard (FIPS) Pub. 197 [2]で規定されているAdvanced Encryption Standard (AES)アルゴリズムがある。したがって、ブロック長が64ビットのTriple Data Encryption Algorithm [3]にはCCMを使用できない。CCMはブロック暗号アルゴリズムの動作モードとみなすことができる。他の動作モードと同様に、データの関係者間で事前にブロック暗号用の単一鍵を確立しなければならない。したがって、CCMは適切に設計された鍵管理構造の中で実装すべきである。CCMのセキュリティ特性は、少なくとも鍵の秘密性に依存する。

CCM is intended for use in a packet environment, i.e., when all of the data is available in storage before CCM is applied; CCM is not designed to support partial processing or stream processing. The input to CCM includes three elements: 1) data that will be both authenticated and encrypted, called the payload; 2) associated data, e.g., a header, that will be authenticated but not encrypted; and 3) a unique value, called a nonce, that is assigned to the payload and the associated data.

原本 PDF p.8

CCMはパケット環境、すなわちCCMを適用する前にすべてのデータが記憶領域にそろっている状況での使用を意図している。CCMは部分処理やストリーム処理を支援するよう設計されていない。CCMへの入力は3つの要素からなる。1) 認証と暗号化の両方を行うデータ（ペイロードと呼ぶ）、2) ヘッダーなど、認証は行うが暗号化しない関連データ、3) ペイロードおよび関連データに割り当てる一意の値（ノンスと呼ぶ）。

CCM consists of two related processes: generation-encryption and decryption-verification, which combine two cryptographic primitives: counter mode encryption and cipher block chaining-based authentication. Only the forward cipher function of the block cipher algorithm is used within these primitives.

原本 PDF p.8

CCMは、生成・暗号化と復号・検証という関連する2つのプロセスからなり、カウンター・モード暗号化と暗号ブロック連鎖に基づく認証という2つの暗号プリミティブを組み合わせる。これらのプリミティブ内では、ブロック暗号アルゴリズムの順方向暗号関数のみを使用する。

In generation-encryption, cipher block chaining is applied to the payload, the associated data, and the nonce to generate a message authentication code (MAC); then, counter mode encryption is applied to the MAC and the payload to transform them into an unreadable form, called the ciphertext. Thus, CCM generation-encryption expands the size of the payload by the size of the MAC. In decryption-verification, counter mode decryption is applied to the purported ciphertext to recover the MAC and the corresponding payload; then, cipher block chaining is applied to the payload, the received associated data, and the received nonce to verify the correctness of the MAC. Successful verification provides assurance that the payload and the associated data originated from a source with access to the key.

原本 PDF p.8

生成・暗号化では、暗号ブロック連鎖をペイロード、関連データ、ノンスに適用してメッセージ認証コード（MAC）を生成する。次に、カウンター・モード暗号化をMACとペイロードに適用し、暗号文と呼ばれる判読不能な形式に変換する。したがって、CCMによる生成・暗号化では、MACの長さ分だけペイロードのサイズが増える。復号・検証では、暗号文とされるデータにカウンター・モード復号を適用し、MACと対応するペイロードを復元する。次に、ペイロード、受信した関連データ、受信したノンスに暗号ブロック連鎖を適用して、MACの正しさを検証する。検証に成功すると、ペイロードと関連データが鍵へのアクセス権を持つ送信元に由来することが保証される。

A MAC provides stronger assurance of authenticity than a checksum or an error detecting code. The verification of a (non-cryptographic) checksum or an error detecting code is designed to detect only accidental modifications of the data, while the verification of a MAC, as occurs in CCM, is designed to detect intentional, unauthorized modifications of the data, as well as accidental modifications.

原本 PDF p.8

MACは、チェックサムや誤り検出符号より強い真正性保証を提供する。チェックサム（非暗号学的）または誤り検出符号の検証は、データの偶発的な変更のみを検出するよう設計されている。一方、CCMで用いられるMACの検証は、データの意図的かつ未認可の変更と偶発的な変更の両方を検出するよう設計されている。

This specification of CCM is intended to be compatible with the use of CCM within the draft amendment [4] to the IEEE Standard 802.11 for wireless local area networks [5].

原本 PDF p.8

このCCM仕様は、改訂案[4]（無線ローカル・エリア・ネットワーク向けIEEE Standard 802.11 [5]）内でCCMを使用する場合との互換性を意図している。

5.2 Cryptographic Primitives

原本 PDF p.13

5.2 暗号プリミティブ

The CCM specification essentially combines two cryptographic mechanisms that are based on the forward cipher function. One mechanism is the Counter (CTR) mode for confidentiality, which is specified for general use in the first Part of this Recommendation [6]. The CTR mode requires the generation of a sufficiently long sequence of blocks called the counter blocks. The counter blocks must be distinct within a single invocation and across all other invocations of the CTR mode under any given key, but they need not be secret. This requirement on the counter blocks extends to the CCM mode. See [6] for further discussion of the generation of counter blocks; see Section 5.4 below for an additional requirement on the counter blocks in CCM.

原本 PDF p.13

CCM仕様は、基本的に順方向暗号関数に基づく2つの暗号機構を組み合わせる。一方は機密性を提供するカウンター（CTR）モードであり、本勧告の第1部[6]で一般用途向けに規定されている。CTRモードでは、カウンター・ブロックと呼ばれる十分に長いブロック列を生成する必要がある。カウンター・ブロックは、単一の呼出し内および所与の鍵の下での他のすべてのCTRモード呼出し間で互いに異ならなければならないが、秘密である必要はない。このカウンター・ブロックに関する要件はCCMモードにも適用される。カウンター・ブロックの生成に関する詳細は[6]を参照し、CCMのカウンター・ブロックに対する追加要件については以下の5.4節を参照する。 (must)

The other cryptographic mechanism within CCM is an adaptation of the cipher block chaining (CBC) technique from [6] to provide assurance of authenticity. Specifically, the CBC technique with an initialization vector of zero is applied to the data to be authenticated; the final block of the resulting CBC output, possibly truncated, serves as a message authentication code (MAC) of the data. The algorithm for generating a MAC in this fashion is commonly called CBC-MAC. This Recommendation does not approve CBC-MAC as an authentication mode outside of the context of the CCM specification; however, a variation of CBC-MAC is proposed for general use in the second Part of this Recommendation [7].

原本 PDF p.13

If \(a=0\), as indicated by the \(\mathit{Adata}\) field in the first octet of \(B_0\), then there are no blocks devoted to the associated data in the formatted data. The value \(a\) is encoded according to the following three cases:

原本 PDF p.19

• If \(0 < a < 2^{16}-2^{8}\), then \(a\) is encoded as \([a]_{16}\), i.e., two octets.

• If \(2^{32} \le a < 2^{64}\), then \(a\) is encoded as \(\mathrm{0xff} \parallel \mathrm{0xff} \parallel [a]_{64}\), i.e., ten octets.

原本 PDF p.20

For example, if \(a=2^{16}\), the encoding of \(a\) is 11111111 11111110 00000000 00000001 00000000 00000000.

例えば\(a=2^{16}\)の場合、\(a\)の符号化は11111111 11111110 00000000 00000001 00000000 00000000である。

The formatting of distinct sets of associated data will not overlap, because for distinct values of \(a\), the leading bits of the encodings of \(a\) are distinct: in the first case, the first octet will not be 0xff as it will for the second and third cases; the second and third cases can be distinguished by the second octet. 原本 PDF p.20

B.1 Authentication Assurance

原本 PDF p.21

B.1 認証保証

The decryption-verification process determines whether a purported ciphertext input is, in fact, a ciphertext, i.e., the output of the generation-encryption process with the given key, associated data string, and nonce. The basis of the CCM authentication assurance is the scarcity of ciphertexts, which suggests that an attacker, i.e., a party without access to the key or to the generation-encryption process, cannot easily generate a ciphertext. Therefore, any purported ciphertext that passes the decryption-verification process was probably generated legitimately.

原本 PDF p.21

復号・検証プロセスは、暗号文とされる入力が実際に暗号文であるか、すなわち所与の鍵、関連データ列、ノンスを用いた生成・暗号化プロセスの出力であるかを判定する。CCMの認証保証は、暗号文が希少であることを根拠とする。これは、攻撃者（すなわち鍵または生成・暗号化プロセスにアクセスできない当事者）が暗号文を容易に生成できないことを示唆する。したがって、復号・検証プロセスを通過した暗号文とされるデータは、正当に生成された可能性が高い。

For any purported ciphertext that is at least \(\mathit{Tlen}\) bits long, the rightmost \(\mathit{Tlen}\) bits correspond to an encrypted MAC, and the remaining bits correspond to an encrypted payload. The decryption-verification process checks the correctness of the MAC for the payload, the associated data string, and the nonce. Depending on the result, the output is either the error message INVALID or the payload. The nature of the authentication assurance, in turn, depends on the output:

原本 PDF p.21

\(\mathit{Tlen}\)ビット以上の長さを持つ暗号文とされるデータでは、右端の\(\mathit{Tlen}\)ビットが暗号化MACに相当し、残りのビットは暗号化ペイロードに相当する。復号・検証プロセスは、ペイロード、関連データ列、ノンスについてMACの正しさを検査する。その結果に応じて、出力はエラー・メッセージINVALIDまたはペイロードのいずれかとなる。認証保証の性質は、さらに出力に依存する：

•If the output is INVALID, then the payload and the associated data string cannot both be authentic, i.e., they cannot have originated from a source that executed the generation-encryption process on them with the given nonce to produce the purported ciphertext.

原本 PDF p.21

•出力がINVALIDの場合、ペイロードと関連データ列の両方が真正であることはあり得ない。すなわち、所与のノンスを使って生成・暗号化プロセスを実行し、暗号文とされるデータを生成した送信元に由来するものではない。

•If the output is the payload, then the design of the mode provides assurance that the payload and the associated data are authentic. This assurance, however, is not absolute: an attacker can generate a ciphertext with a certain probability.

原本 PDF p.21

•出力がペイロードの場合、モードの設計によって、ペイロードおよび関連データが真正であるという保証が提供される。ただし、この保証は絶対ではない。攻撃者が一定の確率で暗号文を生成できる場合がある。

In the second case, the scarcity of ciphertexts and, thus, the expected probability that an attacker can guess a ciphertext, is regulated by the size of \(\mathit{Tlen}\). In particular, the probability is no greater than 1 in \(2^{\mathit{Tlen}}\) that a single inauthentic purported ciphertext will pass the decryption-verification process with a given associated data string and nonce. Of course, an attacker may attempt to present many purported ciphertexts to the decryption-verification process and thereby increase the probability that at least one of them will turn out to be a true ciphertext.

原本 PDF p.21

第2の場合、暗号文の希少性、したがって攻撃者が暗号文を推測できると期待される確率は、\(\mathit{Tlen}\)のサイズによって制御される。特に、所与の関連データ列とノンスを用いたとき、真正でない暗号文とされる単一のデータが復号・検証プロセスを通過する確率は\(2^{\mathit{Tlen}}\)分の1以下である。もちろん、攻撃者は多数の暗号文とされるデータを復号・検証プロセスに提示し、そのうち少なくとも1つが本物の暗号文となる確率を高めようとする場合がある。

Moreover, an attacker may be able to choose the purported ciphertext in such a way as to control every bit of the corresponding payload, as described in [9].* Therefore, if the output of the decryption-verification process is a payload, the contents of the payload do not constitute evidence for its authenticity beyond the assurance that the mode already provides.

原本 PDF p.21

さらに、[9]で説明するとおり、攻撃者は対応するペイロードのすべてのビットを制御するように暗号文とされるデータを選べる場合がある。* したがって、復号・検証プロセスの出力がペイロードである場合、その内容はモードがすでに提供する保証を超える真正性の証拠とはならない。

Also, an attacker may be able to intercept a legitimate ciphertext and “replay” it for verification at a later time. To defend against such an event, the controlling protocol or application should typically provide the receiver with a means to detect replayed messages, out-of-sequence messages, and missing messages, for example, by numbering legitimate messages sequentially.

原本 PDF p.22

また、攻撃者は正当な暗号文を傍受し、後刻の検証時にそれを「再送」できる場合がある。このような事象を防ぐため、制御するプロトコルまたはアプリケーションは通常、正当なメッセージに連番を付けるなどして、受信者が再送メッセージ、順序が前後したメッセージ、および欠落したメッセージを検出する手段を提供すべきである。

B.2 Selection of the MAC Length

原本 PDF p.22

B.2 MAC長の選択

Larger values of \(\mathit{Tlen}\) provide greater authentication assurance, as described in Section B.1. The performance tradeoff is that larger values of \(\mathit{Tlen}\) require more bandwidth/storage for the ciphertext.

原本 PDF p.22

B.1節で説明したように、\(\mathit{Tlen}\)の値が大きいほど、認証の保証が強くなる。性能面のトレードオフとして、\(\mathit{Tlen}\)の値が大きいほど、暗号文に必要な帯域幅またはストレージが増加する。

Although the formatting function in Appendix A permits \(\mathit{Tlen}\) to be any integer multiple of 16 between 32 and 128, inclusive, a value of \(\mathit{Tlen}\) that is less than 64 shall not be used without a careful analysis of the risks of accepting inauthentic data as authentic.

原本 PDF p.22

付録Aの書式設定関数では、\(\mathit{Tlen}\)を32以上128以下の16の任意の整数倍にできるが、\(\mathit{Tlen}\)が64未満の値は、不真正なデータを真正なものとして受け入れるリスクを慎重に分析せずに使用してはならない。

In particular, a value of \(\mathit{Tlen}\) smaller than 64 should not be used unless the controlling protocol or application environment sufficiently restricts the number of times that the decryption-verification process can return INVALID, across all implementations under any given key. For example, the short duration of a session or, more generally, the low bandwidth of the communication channel may preclude many repeated trials.

原本 PDF p.22

特に、制御するプロトコルまたはアプリケーション環境が、任意の所与の鍵の下にあるすべての実装にわたり、復号・検証プロセスがINVALIDを返し得る回数を十分に制限しない限り、\(\mathit{Tlen}\)が64未満の値を使用すべきではない。例えば、セッション時間が短いこと、またはより一般的には通信チャネルの帯域幅が小さいことにより、多数回の試行が行えなくなる場合がある。

Similarly, for larger values of \(\mathit{Tlen}\), the controlling protocol or the application environment should limit the number of inauthentic input sets that may be presented to the decryption-verification process to a number commensurate with the value of the protected data.

原本 PDF p.22

同様に、\(\mathit{Tlen}\) の値が大きい場合、制御するプロトコルまたはアプリケーション環境は、復号・検証プロセスに提示され得る不真正な入力セットの数を、保護対象データの価値に見合う数に制限すべきである。

This guidance can be quantified in terms of the following two bounds: 1) the highest acceptable probability for an inauthentic message to pass the decryption-verification process, and 2) a limit on the number of times that the output is the error message INVALID before the key is retired, across all implementations of the decryption-verification process under the key. Given estimates of these quantities, denoted \(\mathit{Risk}\) and \(\mathit{MaxErrs}\), respectively, \(\mathit{Tlen}\) should satisfy the following inequality:

原本 PDF p.22

この指針は、次の2つの上限によって定量化できる。1) 不真正なメッセージが復号・検証プロセスを通過する許容可能な最大確率、2) 鍵を廃棄するまでに、当該鍵の下にある復号・検証プロセスのすべての実装にわたり、出力がエラーメッセージ INVALID となる回数の上限。これらの量の推定値をそれぞれ \(\mathit{Risk}\) および \(\mathit{MaxErrs}\) と表記すると、\(\mathit{Tlen}\) は次の不等式を満たすべきである。

\[ \mathit{Tlen} \ge \lg(\mathit{MaxErrs} / \mathit{Risk})\,. \]
原本 PDF p.22
\[ \mathit{Tlen} \ge \lg(\mathit{MaxErrs} / \mathit{Risk})\,. \]

For example, suppose that a system will not output INVALID for more than 1024 messages before retiring the key (i.e., \(\mathit{MaxErrs}=2^{10}\)), and that the users can tolerate about a one in a million chance that the system will accept an inauthentic message (i.e., \(\mathit{Risk}=2^{-20}\)). In this case, \(\mathit{Tlen}\) may be as low as 32. On the other hand, if \(\mathit{MaxErrs}=2^{32}\) and \(\mathit{Risk}=2^{-32}\), then \(\mathit{Tlen}\) should be at least 64.

原本 PDF p.22

例えば、システムが鍵を廃棄するまでに INVALID を出力するメッセージが1024個を超えない（すなわち、\(\mathit{MaxErrs}=2^{10}\)）とし、かつ、利用者が、システムが不真正なメッセージを受け入れる確率を約100万分の1まで許容できる（すなわち、\(\mathit{Risk}=2^{-20}\)）とする。この場合、\(\mathit{Tlen}\) は32まで小さくしてもよい。一方、\(\mathit{MaxErrs}=2^{32}\) かつ \(\mathit{Risk}=2^{-32}\) の場合、\(\mathit{Tlen}\) は少なくとも64とするべきである。

C.4 例4

In the following example, \(\mathit{Klen} = 128\), \(\mathit{Tlen}=112\), \(\mathit{Nlen} = 104\), \(\mathit{Alen} = 524288\), and \(\mathit{Plen} = 256\). The associated data string is too large to comfortably present in its entirety; therefore, the given string of the first sixteen blocks of the associated data string is concatenated with itself repeatedly to form a string of 524288 bits. Similarly, only the beginning and the end of the resulting formatted data string \(B\) are presented.
