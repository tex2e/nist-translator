Abstract

原本 PDF p.4

概要

The Common Configuration Scoring System (CCSS) is a set of measures of the severity of software security configuration issues. CCSS is derived from CVSS, which was developed to measure the severity of vulnerabilities due to software flaws. CCSS can assist organizations in making sound decisions as to how security configuration issues should be addressed and can provide data to be used in quantitative assessments of the overall security posture of a system. This report defines proposed measures for CCSS and equations to be used to combine the measures into severity scores for each configuration issue. The report also provides several examples of how CCSS measures and scores would be determined for a diverse set of security configuration issues.

原本 PDF p.4

共通設定評価システム（Common Configuration Scoring System: CCSS）は、ソフトウェアのセキュリティ設定上の問題の深刻度を測る一連の尺度です。CCSS は CVSS から派生したものであり、CVSS は、ソフトウェアの欠陥に起因する脆弱性の深刻度を測るために開発されました。CCSS は、セキュリティ設定上の問題にどのように対処すべきかについて、組織が適切な判断を下すのを支援でき、システム全体のセキュリティ態勢の定量的な評価で使用するデータを提供できます。この報告書は、CCSS の提案する尺度と、それらの尺度を組み合わせて各設定上の問題の深刻度スコアにするための式を定義します。また、多様なセキュリティ設定上の問題について、CCSS の尺度とスコアをどのように決定するかの例も、いくつか示します。

原本 PDF p.7

1.1 Categories of System Vulnerabilities

原本 PDF p.7

1.1 システムの脆弱性の分類

There are many ways in which the vulnerabilities of a system can be categorized. For the purposes of vulnerability scoring, this report uses three high-level vulnerability categories: software flaws, security configuration issues, and software feature misuse.3 These categories are described below.

原本 PDF p.7

システムの脆弱性は、さまざまな方法で分類できます。脆弱性のスコアリングを目的として、この報告書では、ソフトウェアの欠陥、セキュリティ設定上の問題、ソフトウェア機能の誤用という 3 つの上位の脆弱性分類を用います。3これらの分類を以下に説明します。

A software flaw vulnerability is caused by an unintended error in the design or coding of software. An example is an input validation error, such as user-provided input not being properly evaluated for malicious character strings and overly long values associated with known attacks. Another example is a race condition error that allows the attacker to perform a specific action with elevated privileges.

原本 PDF p.7

ソフトウェアの欠陥に関する脆弱性は、ソフトウェアの設計またはコーディングにおける意図しない誤りによって生じます。例として、入力検証の誤りがあります。これは、利用者が与えた入力に対し、既知の攻撃に関連する悪意のある文字列や過度に長い値が適切に評価されないといったものです。別の例として、攻撃者が昇格した権限で特定の操作を実行できてしまう、競合状態の誤りがあります。

A security configuration setting is an element of a software’s security that can be altered through the software itself. Examples of settings are an operating system offering access control lists that set the privileges that users have for files, and an application offering a setting to enable or disable the encryption of sensitive data stored by the application. A security configuration issue vulnerability involves the use of security configuration settings that negatively affect the security of the software.

原本 PDF p.7

セキュリティ設定とは、ソフトウェア自体を通じて変更できる、ソフトウェアのセキュリティの要素です。設定の例として、利用者がファイルに対して持つ権限を設定するアクセス制御リストを提供するオペレーティングシステムや、アプリケーションが保存する機微なデータの暗号化を有効または無効にする設定を提供するアプリケーションがあります。セキュリティ設定上の問題に関する脆弱性は、ソフトウェアのセキュリティに悪影響を及ぼすセキュリティ設定の使用に関わります。

A software feature is a functional capability provided by software. A software feature misuse vulnerability is a vulnerability in which the feature also provides an avenue to compromise the security of a system. These vulnerabilities are caused by the software designer making trust assumptions that permit the software to provide beneficial features, while also introducing the possibility of someone violating the trust assumptions to compromise security. For example, email client software may contain a feature that renders HTML content in email messages. An attacker could craft a fraudulent email message that contains hyperlinks that, when rendered in HTML, appear to the recipient to be benign, but actually take the recipient to a malicious web site when they are clicked on. One of the trust assumptions in the design of the HTML content rendering feature was that users would not receive malicious hyperlinks and click on them.

原本 PDF p.7

Software feature misuse vulnerabilities are introduced during the design of the software or a component of the software (e.g., a protocol that the software implements). Trust assumptions may have been explicit—for example, a designer being aware of a security weakness and determining that a separate security control would compensate for it. However, trust assumptions are often implicit, such as creating a feature without first evaluating the risks it would introduce. Threats may also change over the lifetime of software or a protocol used in software. For example, the Address Resolution Protocol (ARP) trusts that an ARP reply contains the correct mapping between Media Access Control (MAC) and Internet Protocol (IP) addresses. The ARP cache uses that information to provide a useful service—to enable sending data between devices within a local network. However, an attacker could generate false ARP messages to poison a system’s ARP table and thereby launch a denial-of-service or a man-in-the-middle attack. The ARP protocol was standardized over 25 years ago4, and threats have changed a great deal since then, so the trust assumptions inherent in its design then are unlikely to still be reasonable today.

There may also be confusion regarding misuse vulnerabilities for features that can be enabled or disabled—in a way, configured—versus security configuration issues. The key difference is that for a misuse vulnerability, the configuration setting enables or disables the entire feature, and does not specifically alter just its security; for a security configuration issue vulnerability, the configuration setting alters only the software’s security. For example, a setting that disables all use of HTML in emails has a significant impact on both security and functionality, so a vulnerability related to this setting would be a misuse vulnerability. 1.2 The Need for Vulnerability Measurement and Scoring

原本 PDF p.8

1.2 脆弱性の測定とスコアリングの必要性

No system is 100% secure: every system has vulnerabilities. At any given time, a system may not have any known software flaws, but security configuration issues and software feature misuse vulnerabilities are always present. Misuse vulnerabilities are inherent in software features because each feature must be based on trust assumptions—and those assumptions can be broken, albeit involving significant cost and effort in some cases. Security configuration issues are also unavoidable for two reasons. First, many configuration settings increase security at the expense of reducing functionality, so using the most secure settings could make the software useless or unusable. Second, many security settings have both positive and negative consequences for security. An example is the number of consecutive failed authentication attempts to permit before locking out a user account. Setting this to 1 would be the most secure setting against password guessing attacks, but it would also cause legitimate users to be locked out after mistyping a password once, and it would also permit attackers to perform denial-of-service attacks against users more easily by generating a single failed login attempt for each user account.

原本 PDF p.8

100% 安全なシステムはなく、どのシステムにも脆弱性があります。ある時点で、システムに既知のソフトウェアの欠陥がない場合があっても、セキュリティ設定上の問題とソフトウェア機能の誤用に関する脆弱性は常に存在します。誤用に関する脆弱性はソフトウェア機能に内在します。各機能は信頼の前提に基づいていなければならず、その前提は、場合によっては多大なコストと労力を要するものの、破られる可能性があるためです。セキュリティ設定上の問題も、2 つの理由から避けられません。第 1 に、多くの設定は、機能を犠牲にしてセキュリティを高めるものであり、最も安全な設定を使用すると、ソフトウェアが役に立たなくなったり、使えなくなったりするおそれがあります。第 2 に、多くのセキュリティ設定は、セキュリティに対して良い結果と悪い結果の両方をもたらします。例として、利用者アカウントをロックアウトするまでに許容する連続した認証失敗の回数があります。これを 1 に設定すると、パスワード推測攻撃に対しては最も安全な設定になりますが、正規の利用者も一度パスワードを打ち間違えただけでロックアウトされてしまううえ、攻撃者が各利用者アカウントに対してログイン失敗を 1 回生成するだけで、利用者に対するサービス拒否攻撃をより容易に実行できるようになります。

Because of the number of vulnerabilities inherent in security configuration settings and software feature misuse possibilities, plus the number of software flaw vulnerabilities on a system at any given time, there may be dozens or hundreds of vulnerabilities on a single system. These vulnerabilities are likely to have a wide variety of characteristics. Some will be very easy to exploit, while others will only be exploitable under a combination of highly unlikely conditions. One vulnerability might provide root-level access to a system, while another vulnerability might only permit read access to an insignificant file. Ultimately, organizations need to know how difficult it is for someone to exploit each vulnerability and, if a vulnerability is exploited, what the possible impact would be.

原本 PDF p.8

セキュリティ設定に内在する脆弱性の数とソフトウェア機能の誤用の可能性に加え、ある時点でシステムに存在するソフトウェアの欠陥に関する脆弱性の数も考慮すると、1 つのシステムに数十から数百の脆弱性が存在する場合があります。これらの脆弱性は、非常に多様な特性を持つと考えられます。非常に悪用しやすいものがある一方で、可能性が極めて低い条件が重なった場合にのみ悪用できるものもあります。ある脆弱性はシステムへの root レベルのアクセスをもたらす可能性があり、別の脆弱性は重要でないファイルへの読み取りアクセスしか許さない可能性があります。結局のところ、組織は、各脆弱性を悪用することがどれほど難しいか、また、脆弱性が悪用された場合にどのような影響が考えられるかを知る必要があります。

If vulnerability characteristics related to these two concepts were measured and documented in a consistent, methodical way, the measurement data could be used by quantitative risk assessment methodologies for determining which vulnerabilities are most important for an organization to address using its limited resources. For example, when planning the security configuration settings for a new system, an organization could use vulnerability measurements as part of determining the relative importance of particular settings and identifying the settings causing the greatest increase in risk. Vulnerability measurement is also useful when evaluating the security of software features, such as identifying the vulnerabilities in those features that should have compensating controls applied to reduce their risk (for example, antivirus software to scan email attachments and awareness training to alter user behavior) and determining which features should be disabled because their risk outweighs the benefit that they provide.

原本 PDF p.8

これら 2 つの概念に関する脆弱性の特性が、一貫した体系的な方法で測定・文書化されていれば、その測定データを定量的リスク評価の方法論で使用して、限られた資源のなかで組織がどの脆弱性への対処を最も優先すべきかを判断できます。たとえば、新しいシステムのセキュリティ設定を計画する際、組織は、脆弱性の測定を、特定の設定の相対的な重要度の判断や、リスクを最も増大させる設定の特定の一環として使用できます。脆弱性の測定は、ソフトウェア機能のセキュリティを評価する際にも有用です。たとえば、リスクを低減するために補完的な管理策（たとえば、電子メールの添付ファイルをスキャンするウイルス対策ソフトウェアや、利用者の行動を変えるための意識向上トレーニング）を適用すべき機能の脆弱性を特定したり、リスクが提供する利益を上回るために無効にすべき機能を判断したりする場合です。

Having consistent measures for all types of system vulnerabilities has additional benefits. Organizations can compare the relative severity of different vulnerabilities from different software packages and on different systems. Software vendors can track the characteristics of a product’s vulnerabilities over time to determine if its security is improving or declining. Software vendors can also use the measures to communicate to their customers the severity of the vulnerabilities in their products. Auditors and others performing security assessments can check systems to ensure that they do not have unmitigated vulnerabilities with certain characteristics, such as high impact measures or high overall severity scores.

Although having a set of measures for a vulnerability provides the level of detail necessary for in-depth analysis, sometimes it is more convenient for people to have a single measure for each vulnerability. So quantitative measures can be combined into a score—a single number that provides an estimate of the overall severity of a vulnerability. Vulnerability scores are not as quantitative as the measures that they are based on, so they are most helpful for general comparisons, such as a vulnerability with a score of 10 (on a 0 to 10 scale) being considerably more severe than a vulnerability with a score of 4. Small scoring differences, such as vulnerabilities with scores of 4.8 and 5.1, do not necessarily indicate a significant difference in severity because of the margin of error in individual measures and the equations that combine those measures.

脆弱性に対する一連の尺度があれば、詳細な分析に必要な水準の詳細が得られますが、脆弱性ごとに単一の尺度があるほうが便利な場合もあります。そのため、定量的な尺度を組み合わせて、脆弱性の総合的な深刻度の推定値を示す単一の数値であるスコアにすることができます。脆弱性のスコアは、その基になる尺度ほど定量的ではないため、一般的な比較に最も役立ちます。たとえば、スコアが 10（0 から 10 の尺度で）の脆弱性は、スコアが 4 の脆弱性よりもかなり深刻である、といった比較です。スコアが 4.8 と 5.1 の脆弱性のような小さなスコアの差は、個々の尺度とそれらを組み合わせる式に誤差の幅があるため、必ずしも深刻度の大きな違いを示すものではありません。

2. CCSS の指標

This section defines the metrics that comprise the CCSS specification. The CCSS metrics are organized into three groups: base, temporal, and environmental. Base metrics describe the characteristics of a configuration issue that are constant over time and across user environments. Temporal metrics describe the characteristics of configuration issues that can change over time but remain constant across user environments. Environmental metrics are used to customize the base and temporal scores based on the characteristics of a specific user environment. 2.1 Base Metrics

2.1 基本評価基準

This section describes the base metrics, which measure the characteristics of a security configuration issue that are constant with time and across user environments. The base metrics measure two aspects of vulnerability severity: Exploitability and Impact.

原本 PDF p.12

この節では、基本評価基準を説明します。基本評価基準は、時間が経過しても、また利用者の環境が異なっても変わらない、セキュリティ設定上の問題の特性を測定します。基本評価基準は、脆弱性の深刻度の 2 つの側面、すなわち悪用可能性と影響を測定します。

2.1.1 Exploitability
原本 PDF p.12
2.1.1 悪用可能性

The Exploitability of a security configuration issue can be captured using the Access Vector, Authentication, Access Complexity, and Exploitation Method metrics. These metrics are adapted from the CVSS and CMSS specifications and reinterpreted in the context of security configuration issues.

原本 PDF p.12

セキュリティ設定上の問題の悪用可能性は、アクセスベクトル、認証、アクセスの複雑さ、悪用方法の各指標を使って捉えることができます。これらの指標は、CVSS と CMSS の仕様から転用し、セキュリティ設定上の問題の文脈で再解釈したものです。

2.1.1.1 Exploitation Method (EM)
原本 PDF p.12
2.1.1.1 悪用方法（EM）

Vulnerabilities caused by security configuration issues can be taken advantage of in two ways: actively and passively.7 These are indicated in CCSS as an Exploitation Method metric of Active (A) or Passive (P). Some vulnerabilities can be actively exploited, such as an attacker gaining access to a sensitive file because the targeted system is incorrectly configured to permit any user to read the file. Other vulnerabilities passively prevent authorized actions from occurring, such as not permitting a system service or daemon to run or not generating audit log records for security events.

原本 PDF p.12

セキュリティ設定上の問題によって生じる脆弱性は、能動的と受動的の 2 つの方法で悪用され得ます。7これらは、CCSS では、悪用方法の指標が能動的（Active: A）または受動的（Passive: P）として示されます。能動的に悪用できる脆弱性もあります。たとえば、対象のシステムが、どの利用者でも機微なファイルを読み取れるように誤って設定されているために、攻撃者がそのファイルへのアクセスを得る場合です。受動的に、許可された操作の実行を妨げる脆弱性もあります。たとえば、システムサービスやデーモンの実行を許可しない場合や、セキュリティイベントの監査ログ記録を生成しない場合です。

7 It is theoretically possible that a single configuration issue could be taken advantage of both actively and passively, but no examples have been found to date.
原本 PDF p.12
7 理論上は、1 つの設定上の問題が、能動的にも受動的にも悪用される可能性がありますが、これまでのところ、その例は見つかっていません。

The Exploitation Method metric is not used directly in generating CCSS scores, but the definitions for some of the Exploitability base metrics are dependent on the value of the Exploitation Method metric. The Exploitation Method metric is also useful for planning mitigation strategies, because most Passive configuration issues involve an error or policy violation that can be fixed quickly. Active configuration issues have a much wider range of mitigation possibilities and often require significantly more analysis and planning for mitigation than Passive configuration issues.

原本 PDF p.13

悪用方法の指標は、CCSS のスコアの生成には直接使用されませんが、悪用可能性の基本評価基準のいくつかの定義は、悪用方法の指標の値に依存しています。悪用方法の指標は、緩和戦略の計画にも有用です。受動的な設定上の問題の大半は、迅速に修正できる誤りやポリシー違反に関わるためです。能動的な設定上の問題は、緩和の可能性がはるかに幅広く、緩和のために、受動的な設定上の問題よりも大幅に多くの分析と計画を必要とすることが多くあります。

Some organizations may also find the Exploitation Method metric valuable because of how they define availability. For example, an organization might consider a security configuration error that prevents use of a particular system function as an operational concern, not a security concern, and prioritize and remediate it differently. Such errors would all have an Exploitation Method metric value of Passive, so organizations could use the metric to quickly differentiate the configuration issues that they consider operational from the others.

原本 PDF p.13

組織によっては、可用性の定義の仕方によっても、悪用方法の指標が有用だと考える場合があります。たとえば、組織は、特定のシステム機能の使用を妨げるセキュリティ設定上の誤りを、セキュリティ上の懸念ではなく運用上の懸念と考え、優先順位付けや是正を別の方法で行うことがあります。このような誤りはすべて、悪用方法の指標の値が受動的になるため、組織はこの指標を使って、運用上のものと考える設定上の問題を、その他のものと速やかに区別できます。

2.1.1.2 Access Vector (AV)
原本 PDF p.13
2.1.1.2 アクセスベクトル（AV）

The Access Vector metric reflects the access required to exploit the configuration issue. To produce an Access Vector score for a configuration issue, consider what access to the system the exploiter8 must possess in order to exploit the issue. The possible values for this metric are listed in Table 1. The more remote an exploiter can be, the greater the vulnerability score.

原本 PDF p.13

アクセスベクトルの指標は、設定上の問題を悪用するために必要なアクセスを反映します。設定上の問題のアクセスベクトルのスコアを求めるには、悪用する者8がその問題を悪用するために、システムへのどのようなアクセスを持っていなければならないかを考えます。この指標の取り得る値を表 1 に示します。悪用する者がより遠隔にいられるほど、脆弱性のスコアは高くなります。

The Access Vector metric is assigned differently depending upon whether the configuration issue can be taken advantage of actively or passively.

原本 PDF p.13

アクセスベクトルの指標は、設定上の問題を能動的に悪用できるか、受動的に悪用できるかに応じて、割り当て方が異なります。

For active exploitation, the metric reflects from where the exploitation can be performed. The score increases with the degree to which an exploiter may be remote from the affected system.

原本 PDF p.13

能動的な悪用の場合、この指標は、悪用をどこから実行できるかを反映します。悪用する者が影響を受けるシステムから遠隔にいられる度合いが大きいほど、スコアは高くなります。

For passive exploitation, this metric reflects from where users or other systems are supposed to be able to perform the action that is being prevented from occurring. The more remote the users or other systems can be, the greater the score.

原本 PDF p.13

受動的な悪用の場合、この指標は、妨げられている操作を、利用者や他のシステムがどこから実行できるはずであるかを反映します。利用者や他のシステムがより遠隔にいられるほど、スコアは高くなります。

原本 PDF p.13
8 「悪用する者」（exploiter）という用語は、セキュリティ設定に起因する脆弱性を悪用している当事者を指します。場合によっては、許可された利用者が、そのような脆弱性を、多くの場合は悪用しているという認識なしに、意図せず悪用することがあります。そのため、この文書では、文脈が意識的な攻撃であることを明確に示す場合を除き、「攻撃者」などの用語を避けています。

2.1.1.3 Authentication (Au)
原本 PDF p.14
2.1.1.3 認証（Au）

The Authentication metric measures the number of times an exploiter must authenticate to a target in order to exploit a vulnerability. This metric does not gauge the strength or complexity of the authentication process, only that an exploiter is required to provide credentials before an exploit may occur. The possible values for this metric are listed in Table 2. The fewer authentication instances that are required, the higher the score.

原本 PDF p.14

認証の指標は、脆弱性を悪用するために、悪用する者が対象に対して認証しなければならない回数を測定します。この指標は、認証プロセスの強度や複雑さを評価するものではなく、悪用が発生する前に、悪用する者が認証情報を提供することが求められるという点のみを評価します。この指標の取り得る値を表 2 に示します。必要な認証の回数が少ないほど、スコアは高くなります。

It is important to note that the Authentication metric is different from Access Vector. Here, authentication requirements are considered once the system has already been accessed. Specifically, for locally exploitable vulnerabilities, this metric should only be set to “Single” or “Multiple” if authentication is needed beyond what is required to log into the system. An example of a locally exploitable vulnerability that requires authentication is one affecting a database engine listening on a UNIX domain socket (or some other non-network interface). If the user9 must authenticate as a valid database user in order to exploit the vulnerability, then this metric should be set to “Single.”

原本 PDF p.14

認証の指標がアクセスベクトルとは異なることに注意することが重要です。ここでは、システムにすでにアクセスした後の認証要件を考慮します。具体的には、ローカルで悪用できる脆弱性では、システムへのログインに必要なもの以上の認証が必要な場合にのみ、この指標を「単一」または「複数」に設定すべきです。認証を必要とする、ローカルで悪用できる脆弱性の例は、UNIX ドメインソケット（またはその他の非ネットワークインターフェース）で待ち受けているデータベースエンジンに影響するものです。利用者9が、脆弱性を悪用するために、有効なデータベース利用者として認証しなければならない場合、この指標は「単一」に設定すべきです。

There are no distinctions between active and passive exploitation in assigning values to this metric.

2.1.1.4 Access Complexity (AC)
原本 PDF p.15
2.1.1.4 アクセスの複雑さ（AC）

The Access Complexity metric reflects the complexity of the attack required to exploit the configuration issue. The Access Complexity metric is assigned differently depending upon whether the configuration issue can be taken advantage of actively or passively.

原本 PDF p.15

アクセスの複雑さの指標は、設定上の問題を悪用するために必要な攻撃の複雑さを反映します。アクセスの複雑さの指標は、設定上の問題を能動的に悪用できるか、受動的に悪用できるかに応じて、割り当て方が異なります。

For active exploitation, this metric measures the complexity of the actions required to exploit the vulnerability once an exploiter has gained access to the target system. For example, consider a default user account and password for a network service: once the target system is located, the exploiter can access the network service at will. Other vulnerabilities, however, may require additional steps in order to be exploited. For example, a vulnerability in an email client is only exploited after the user downloads and opens a tainted attachment. The lower the required complexity, the higher the score.

原本 PDF p.15

能動的な悪用の場合、この指標は、悪用する者が対象のシステムにアクセスした後に、脆弱性を悪用するために必要な操作の複雑さを測定します。たとえば、ネットワークサービスのデフォルトの利用者アカウントとパスワードを考えます。対象のシステムが特定されれば、悪用する者はそのネットワークサービスに自由にアクセスできます。一方、他の脆弱性は、悪用するために追加の手順が必要な場合があります。たとえば、電子メールクライアントの脆弱性は、利用者が汚染された添付ファイルをダウンロードして開いた後にのみ悪用されます。必要な複雑さが低いほど、スコアは高くなります。

For passive exploitation, this metric is set to the lowest complexity because the outcome of the vulnerability, such as not permitting a service to run, has already occurred or is constantly occurring—no additional actions are needed.

原本 PDF p.15

受動的な悪用の場合、サービスの実行を許可しないなど、脆弱性の結果がすでに生じているか、常に生じているため、追加の操作は必要なく、この指標は最も低い複雑さに設定されます。

The possible values for this metric are listed in Table 3. The lower the required complexity, the higher the vulnerability score.

2.1.2 Impact
原本 PDF p.16
2.1.2 影響

The impact of a software security configuration issue can be captured using the Confidentiality Impact, Integrity Impact, and Availability Impact metrics. These metrics are adapted from the CVSS specification and reinterpreted in the context of security configuration issues. These three Impact metrics measure how exploitation of a configuration issue could directly affect a targeted system. The Impact metrics independently reflect the degree of loss of confidentiality, integrity, and availability. For example, exploitation of a particular configuration issue could cause a partial loss of integrity and availability, but no loss of confidentiality.

原本 PDF p.16

ソフトウェアのセキュリティ設定上の問題の影響は、機密性への影響、完全性への影響、可用性への影響の各指標を使って捉えることができます。これらの指標は、CVSS の仕様から転用し、セキュリティ設定上の問題の文脈で再解釈したものです。これら 3 つの影響の指標は、設定上の問題の悪用が、対象のシステムに直接どのような影響を及ぼし得るかを測定します。影響の指標は、機密性、完全性、可用性の損失の度合いを、それぞれ独立に反映します。たとえば、特定の設定上の問題の悪用により、完全性と可用性の部分的な損失は生じるものの、機密性の損失は生じない場合があります。

For many configuration issues, the possible impact from exploitation is dependent on the privileges held by the user or application (including services). For example, a user account could have restricted privileges or full root-level privileges; exploiting many vulnerabilities would cause a greater impact if full privileges were available. However, the privileges available through exploitation are environment-specific. CCSS prevents environment-specific privileges from affecting the base impact metrics by assuming for those metrics that the generally accepted best practices for the privileges are being employed.10

原本 PDF p.16

多くの設定上の問題では、悪用による影響の可能性は、利用者またはアプリケーション（サービスを含む）が保持する権限に依存します。たとえば、利用者アカウントには、制限された権限が与えられている場合もあれば、完全な root レベルの権限が与えられている場合もあります。多くの脆弱性は、完全な権限が利用できる場合、悪用による影響がより大きくなります。ただし、悪用によって利用できる権限は、環境固有です。CCSS は、基本の影響の指標について、権限に関して一般に受け入れられているベストプラクティスが採用されていると仮定することで、環境固有の権限が基本の影響の指標に影響しないようにしています。10

CCSS allows organizations to take into account different privileges that they may provide in their environments. This is done through a combination of base and environmental metrics. The base metric, Privilege Level (PL), indicates the level of unauthorized access that an attacker could gain, such as impersonating a user or gaining full access to an application or an operating system. Possible values for Privilege Level are Root Level (R), User Level (U), Application Level (A), and Not Defined (ND). The environmental metrics that use the Privilege Level are described in Section 2.3.3.1.

原本 PDF p.17

CCSS では、組織が、自らの環境で提供する可能性のあるさまざまな権限を考慮に入れることができます。これは、基本評価基準と環境評価基準を組み合わせることで行われます。基本の指標である権限レベル（PL）は、利用者になりすます、アプリケーションやオペレーティングシステムへの完全なアクセスを得るなど、攻撃者が得られる無許可のアクセスのレベルを示します。権限レベルの取り得る値は、ルートレベル（R）、ユーザーレベル（U）、アプリケーションレベル（A）、未定義（ND）です。権限レベルを使用する環境評価基準は、第 2.3.3.1 節で説明します。

2.2.1 General Exploit Level (GEL)
原本 PDF p.19
2.2.1 一般的な悪用レベル（GEL）

The General Exploit Level metric measures the prevalence of attacks against a security configuration issue—how often any vulnerable system is likely to come under attack. If a security configuration issue could be exploited more widely with the use of exploit code, the prevalence of attacks may be related to the current state of exploit techniques or exploit code availability. Public availability of easy-to-use exploit code increases the number of potential attackers by including those who are unskilled, thereby increasing the severity of the vulnerability. The availability of automated exploit code also increases the number of attacks each attacker can launch. However, note that attacks may not require exploit code. For example, consider a security configuration issue that can be attacked by sending a user an email with instructions to perform actions that result in an exploit. The prevalence of this type of attack would be measured by the frequency with which the exploit email is received by users on a typical vulnerable system.

原本 PDF p.19

2.2.2 General Remediation Level (GRL)
原本 PDF p.19
2.2.2 一般的な是正レベル（GRL）

The General Remediation Level metric measures the availability of remediation measures that can mitigate the vulnerability other than changing the configuration setting or rendering it useless (e.g., disabling the affected feature, removing the software, installing a third-party security control that overrides the setting). Examples of remediation measures include running antivirus software on a system to restrict which emails a user can read and configuring a host-based firewall to block incoming network connection attempts from external hosts. Remediation measures do not have to be limited to those that are internal to the system—options such as using network-based security controls (e.g., network firewalls, network-based antivirus software) and training users on avoiding poor security practices may also be effective. The effectiveness of the available remediation measures determines the General Remediation Level score.

2.3 Environmental Metrics

原本 PDF p.20

2.3 環境評価基準

Differences between environments can have a large effect on the risk that a vulnerability poses to a particular organization and its stakeholders. The CCSS environmental metrics capture the characteristics of a vulnerability that are associated with a particular IT environment. Each organization computing CCSS metrics can determine an appropriate definition of IT environment, such as the entire enterprise or a logical or physical subset of the enterprise (e.g., a facility, a division, a small group of related systems). Since environmental metrics are optional, each includes a metric value that has no effect on the score. This value is used when the analyst feels the particular metric does not apply and wishes to ignore it.

原本 PDF p.20

環境の違いは、脆弱性が特定の組織とそのステークホルダーにもたらすリスクに大きな影響を及ぼし得ます。CCSS の環境評価基準は、特定の IT 環境に関連する脆弱性の特性を捉えます。CCSS の指標を計算する各組織は、IT 環境の適切な定義（たとえば、エンタープライズ全体、またはエンタープライズの論理的もしくは物理的な部分集合（たとえば、施設、部門、関連する少数のシステム群））を決定できます。環境評価基準は任意であるため、それぞれに、スコアに影響しない指標値が含まれています。この値は、アナリストが特定の指標が該当しないと考え、それを無視したい場合に使用されます。

The environmental metrics customize the previously computed base and temporal metrics. The environmental metrics measure three aspects of vulnerability severity: Local Exploit Level, Local Remediation Level, and Local Impact. Similar to the General Exploit Level and General Remediation Level temporal metrics, the Local Exploit Level and Local Remediation Level environmental metrics produce a scaling factor that is applied to the Exploitability components of the base metric. The Local Impact environmental metric comprises several metrics that adjust the base impact metrics to take environment-specific characteristics into account.

原本 PDF p.20

環境評価基準は、先に計算した基本評価基準と時間的評価基準をカスタマイズします。環境評価基準は、脆弱性の深刻度の 3 つの側面、すなわちローカルの悪用レベル、ローカルの是正レベル、ローカルの影響を測定します。時間的評価基準の一般的な悪用レベルと一般的な是正レベルと同様に、環境評価基準のローカルの悪用レベルとローカルの是正レベルは、基本評価基準の悪用可能性の構成要素に適用される倍率を生成します。環境評価基準のローカルの影響は、環境固有の特性を考慮に入れて基本の影響の指標を調整する、複数の指標で構成されます。

The environmental metrics are intended to measure deviations from the assumptions about environments that were used to compute the base and temporal metrics. Therefore, environmental metrics should be scored relative to those assumptions.

原本 PDF p.20

環境評価基準は、基本評価基準と現状評価基準の計算に使用した、環境に関する前提からの乖離を測定することを意図しています。したがって、環境評価基準は、それらの前提に対する相対値としてスコアリングすべきです。

原本 PDF p.20
2.3.1.1 ローカルの脆弱性の蔓延度（LVP）

The Local Vulnerability Prevalence metric measures the prevalence of vulnerable systems in a specific environment. It is intended to approximate the percentage of systems that could be affected by the vulnerability. The Local Vulnerability Prevalence depends both on the prevalence of the configuration issue under scrutiny and the prevalence of its exploitation. For vulnerabilities dependent on user actions, the prevalence of exploitation depends on the probability that users in this environment will perform the actions required for vulnerability exploitation. For example, if 80% of the systems contain a particular vulnerability but only half of the users of those systems are expected to engage in the improper actions that could permit the vulnerability to be exploited, then 40% of the total environment is at risk. Thus, the Local Vulnerability Prevalence would be rated as medium. The Local Vulnerability Prevalence also takes into account, when appropriate, how frequently the vulnerability is relevant for targets, such as how often the vulnerable software is run, how many hours per day the vulnerable software is running, and how much usage exposes the software to threats (for example, how many web sites or emails a user accesses). 2.3.3 Local Impact

2.3.3 ローカルの影響

The Local Impact can be captured using seven environmental metrics. The first three—Environment Confidentiality Impact, Environment Integrity Impact, and Environment Availability Impact—take the place of the corresponding base impact metrics (Confidentiality Impact, Integrity Impact, and Availability Impact). 2.3.3.1 Environment Confidentiality, Integrity, and Availability Impact (EC, EI, EA)
原本 PDF p.22
2.3.3.1 環境の機密性・完全性・可用性への影響（EC、EI、EA）

The Environment Confidentiality, Integrity, and Availability Impact metrics enable the analyst to customize the environmental score if the privileges in the environment differ significantly from best practices related to the vulnerability. For example, suppose that a vulnerability permitted an attacker to gain unauthorized access to a system with the user’s privileges. In the base impact metrics, this would have been recorded as a partial impact to confidentiality, integrity, and availability, under the assumption that the user was running with limited user privileges. However, if a particular environment permitted users to run with full, root-level privileges, then this could be taken into account through the Environment Impact metrics.

3.1 Guidelines

原本 PDF p.26

3.1 ガイドライン

Below are guidelines that should help analysts when scoring security configuration issues. These guidelines are intended primarily for analysts that are creating base scores, although they may be of interest to many others because of the insights they provide into the significance of the base scores and the assumptions made when performing scoring.

原本 PDF p.26

以下は、セキュリティ設定上の問題をスコアリングする際にアナリストの助けとなるガイドラインです。これらのガイドラインは、主に基本スコアを作成するアナリストを対象としていますが、基本スコアの意義や、スコアリングの実施時に置かれる前提についての洞察が得られるため、多くの方の関心を引くかもしれません。

There are potentially multiple vectors and base scores for a single configuration issue, if there is more than one way in which it can be configured that causes a negative security impact. For example, some Windows platforms have an Application Management service, which affects the installation and use of applications. If the service is disabled, it prevents local users from installing and using new applications; if the service is enabled, it allows users to install or remove applications. Because these two cases have different security implications, an analyst would create a vector and a score for each case. In this example, and for many others, there is not necessarily a clear “correct” value, and each organization generally determines its own configuration requirements. An example is the length of time to lock out an account after too many failed login attempts. An analyst would generate two base vectors and scores for this—one for the actual value being higher than policy and one for the actual value being lower than policy—and then the appropriate base vector and score would be selected for each situation based on the organization’s policy and actual system settings.

原本 PDF p.26

The current versions of CCSS, CVSS, and CMSS are all based on sets of assumptions regarding system security, configuration, use, and management. An example is assuming that a software flaw affecting multiple operating systems should be scored based on the security characteristics of the most widely used of those operating systems. These assumptions are made to simplify the scoring process and ensure consistency among analysts. However, to make CCSS, CVSS, and CMSS more valuable for use in quantitative risk assessment and other complex methodologies, these assumptions should be documented in a standardized way. It is hoped that in the future, all three specifications will be updated to add a unified convention for documenting these assertions.

3.1.1 一般

SCORING TIP #1: Configuration issue scoring should not take into account any interaction with other configuration issues, software flaws, or vulnerabilities. That is, each configuration issue should be scored independently. However, if a configuration issue is necessarily dependent on another configuration setting, such as setting A is only used by a system if setting B is enabled, then analysts should assume that the other settings are configured so as to make the issue of interest relevant. For example, if Web server settings are only used by a system if the Web server service is enabled, then analysts should assume the service is enabled.

原本 PDF p.26

SCORING TIP #1: 設定上の問題のスコアリングでは、他の設定上の問題、ソフトウェアの欠陥、脆弱性との相互作用を一切考慮に入れるべきではありません。すなわち、各設定上の問題は、独立してスコアリングすべきです。ただし、設定上の問題が別の設定に必然的に依存している場合、たとえば、設定Aは設定Bが有効な場合にのみシステムで使用される、といった場合には、アナリストは、対象の問題が関連するものとなるように、他の設定が構成されていると仮定すべきです。たとえば、Webサーバーの設定が、Webサーバーサービスが有効な場合にのみシステムで使用されるのであれば、アナリストは、そのサービスが有効であると仮定すべきです。

For example, consider a misconfigured access control list that allows users to place files of their choice (such as malware) in a trusted network share: the impact to the systems of users that download and execute the malware could be much greater than the impact to the target system. However, this is an indirect impact, and should not be considered in base scoring.12

SCORING TIP #3: Because a configuration issue does not state what the desired configuration is, analysts need to consider the plausible possibilities. For an issue with a small number of possible options, such as enabled/disabled, low/medium/high, or 1 through 5, analysts should consider the security implications of each option. For example, in the simplest situation—a setting that can either be enabled or disabled—an analyst should think about the security implications of two cases: 1) the setting is enabled but should be disabled, and 2) the setting is disabled but should be enabled. Only the cases that have a security impact should be analyzed further. Analysts should also eliminate cases that are considered farfetched—exceedingly unlikely to occur. For each remaining case, analysts should create a vector and calculate a base score.

For an issue with a large number of possible settings, such as file privileges for users or the number of seconds for a timeout, it is not feasible to consider all the possible combinations of settings. For example, a system could be set to grant one set of excess privileges to user A, grant a different set of excess privileges to user B, and grant insufficient privileges to user C. However, we cannot score endless possibilities for an issue, so we instead consider the common cases independently. For example, if the issue involved privileges for a system binary used for system management, the case most likely to occur is that users can execute the binary but should not be able to (since it is intended for system administrators). Other broad cases with interesting security implications are users being able to modify or delete the system binary, and no users (including administrators) being able to run the binary. Another example is for a timeout; analysts should consider two cases—the timeout being set too high and too low. After analyzing the selected cases and combinations of cases, the analyst should create a vector for each and calculate a score.

原本 PDF p.27

4.2 CCE-4693-8

4.2 CCE-4693-8

5. Comparing CCSS to CVSS and CMSS

原本 PDF p.39

5. CCSS と CVSS・CMSS の比較

CCSS is based on CVSS and CMSS, so there are many similarities among the three specifications. However, there are some important differences as well. This section provides a brief discussion of the major differences between the specifications. Individuals interested in more details on the differences are encouraged to compare the specifications side-by-side. The specifications have similar structures, making such comparisons easy.15

原本 PDF p.39

CCSS は CVSS と CMSS に基づいているため、3 つの仕様には多くの類似点があります。ただし、いくつかの重要な相違点もあります。この節では、仕様間の主な相違点を簡潔に論じます。相違点の詳細に関心のある方は、仕様を並べて比較することが推奨されます。仕様は構造が似ているため、そのような比較は容易です。15

For the base metrics, all three specifications use the same six metrics and the same equations for calculating scores. The descriptions for each metric have been adjusted to fit the characteristics of the category of vulnerabilities that they cover. The most notable difference is that CCSS also measures the type of exploitation: active or passive. Active exploitation refers to an attacker performing actions to take advantage of a vulnerability, while passive exploitation refers to vulnerabilities that prevent authorized actions from occurring, such as a configuration setting that prevents audit log records from being generated for security events. The Exploitability base metrics in CCSS are defined differently for active and passive exploitation because of the differences in the ease of exploitation.

原本 PDF p.39

基本評価基準については、3 つの仕様はすべて、同じ 6 つの指標と、スコアを計算するための同じ式を使用します。各指標の説明は、対象とする脆弱性の分類の特性に合わせて調整されています。最も顕著な違いは、CCSS が悪用の種類、すなわち能動的か受動的かも測定することです。能動的な悪用とは、攻撃者が脆弱性を悪用するために操作を行うことを指し、受動的な悪用とは、セキュリティイベントの監査ログ記録の生成を妨げる設定など、許可された操作の実行を妨げる脆弱性を指します。CCSS の悪用可能性の基本評価基準は、悪用のしやすさに違いがあるため、能動的な悪用と受動的な悪用とで定義が異なります。

The temporal and environmental components of the three specifications are quite different. The temporal and environmental components of CCSS and CMSS are based on those from CVSS, but have major differences. The temporal metrics in CVSS measure the availability of exploit code, the level of available remediations for the software flaw (e.g., patches), and the confidence in the existence of the vulnerability. These are not relevant for the types of vulnerabilities addressed by CCSS and CMSS, because their vulnerabilities can be exploited without exploit code and are already known to exist. Also, CMSS vulnerabilities and many CCSS vulnerabilities do not have complete remediations. So CCSS and CMSS have similar sets of temporal metrics, quite different from those of CVSS, that address the general prevalence of attacks against the vulnerability and the general effectiveness of available remediation measures, such as using antivirus software or conducting awareness activities.

原本 PDF p.39

3 つの仕様の現状評価基準と環境評価基準の構成要素は、かなり異なっています。CCSS と CMSS の現状評価基準と環境評価基準の構成要素は、CVSS のものに基づいていますが、大きな違いがあります。CVSS の現状評価基準は、エクスプロイトコードが入手可能かどうか、ソフトウェアの欠陥に対して利用可能な是正のレベル（たとえば、パッチ）、脆弱性の存在に対する確信度を測定します。CCSS と CMSS が対象とする種類の脆弱性は、エクスプロイトコードなしで悪用でき、存在がすでに知られているため、これらは関連しません。また、CMSS の脆弱性と多くの CCSS の脆弱性には、完全な是正策がありません。そのため、CCSS と CMSS は、CVSS のものとはかなり異なる、似通った現状評価基準のセットを持ち、脆弱性に対する攻撃の一般的な蔓延度と、ウイルス対策ソフトウェアの使用や意識向上活動の実施など、利用可能な是正措置の一般的な有効性を扱います。

CCSS and CMSS also offer similar sets of environmental metrics, which are considerably more complex than CVSS’s metrics. CVSS has three: Collateral Damage Potential, Target Distribution, and Security Requirements. These metrics are all part of CCSS and CMSS as well, although Target Distribution has been renamed Local Vulnerability Prevalence. Two other metrics have been added to CCSS and CMSS: Perceived Target Value, which measures how attackers value the targets in a specific local environment as opposed to other environments, and Local Remediation Level, which measures the effectiveness of mitigation measures in the local environment. CCSS and CMSS also divide their environmental metrics into two groups: Exploitability and Impact. This allows Exploitability and Impact environmental subscores to be generated for CCSS and CMSS; such subscores are not available in CVSS.

原本 PDF p.39

CCSS と CMSS も、CVSS の指標よりもかなり複雑な、似通った環境評価基準のセットを備えています。CVSS には、副次的損害の可能性、標的の分布、セキュリティ要求の 3 つがあります。これらの指標はいずれも CCSS と CMSS にも含まれますが、標的の分布は、ローカルの脆弱性の蔓延度に名称が変更されています。CCSS と CMSS には、さらに 2 つの指標が追加されています。1 つは認識された標的の価値で、攻撃者が、特定のローカルの環境の標的を、他の環境と比べてどのように評価するかを測定します。もう 1 つはローカルの是正レベルで、ローカルの環境における緩和策の有効性を測定します。CCSS と CMSS は、環境評価基準を、悪用可能性と影響の 2 つのグループにも分けています。これにより、CCSS と CMSS では、悪用可能性と影響の環境サブスコアを生成できますが、CVSS ではそのようなサブスコアは利用できません。
